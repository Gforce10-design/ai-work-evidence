0장 — 왜 "exit 0"은 증거가 아닌가

기술 검증판 2026-09-28 · 원고 최종 수정 2026-09-28

증상
워커가 "완료"라고 답했고 종료코드도 0인데, 그 작업이 실제로 일어났는지 확인할 방법이 없다
원인
종료코드는 프로그램이 정한 성공 신호다. 그 값만으로 작업의 정확성을 보장하지 않는다. 낮은 단계의 사실로 높은 단계를 주장하게 된다
붙일 장치
증거를 7단계로 나누고, 아래 단계가 다 채워져야만 위 단계를 주장할 수 있게 강제하는 검증기
그래도 부족했던 것
사다리를 세워도 옆으로 새는 경로가 셋 더 나왔다. 이 장 후반이 그 이야기다

머리말의 사고는 "그 파일을 읽었다는 걸 확인한 적이 없었다"는 이야기였다. 그런데 그 사고를 겪고 검증 절차를 다듬은 뒤에도 전혀 다른 결의 사고가 또 났다. 이번에는 파일을 읽었느냐 이전에 그 워커가 한 번이라도 실제로 실행된 적이 있는지부터가 문제였다.

"완료됐습니다"라는 로그

리뷰 라운드 하나를 돌렸다. 오케스트레이터가 워커 하나를 호출했고, CLI 프로세스는 종료코드 0으로 끝났고, 표준출력에는 몇 문단짜리 리뷰 텍스트가 찍혔다. 응답 형식을 검사하는 구조 검증기도 통과 판정을 냈다 — 헤더가 있고, 본문이 비어 있지 않고, JSON이 파싱됐다. 로그에는 "완료"라고 적혔고, 그 결과는 다음 판단의 근거로 채택됐다.

몇 라운드 뒤, 독립 리뷰가 이 경로 전체를 다시 열어봤다. 그 워커의 자리는 설정 파일에 이름과 실행 경로만 올라 있었다. 실제 디스패처가 그 이름을 호출한 적은 한 번도 없는 자리였다. 그 라운드에서는 이름이 비슷한 다른 호환 경로가 그 워커 대신 실행됐다. 종료코드 0과 그럴듯한 텍스트는 그 다른 경로가 만들어냈다. 그런데 로그는 이 둘을 원래 부르려 했던 자리의 성과로 세고 있었다.

CLI는 분명 실행됐다. 분명 0을 반환했다. 표준출력도 분명 비어 있지 않았다. 그런데 이 세 가지 사실 중 어느 것도 "내가 부르려 한 그 모델이, 내가 원한 그 작업을, 내가 원한 그 자리에서 했다"는 보장이 되지는 않았다.

$ dispatch --worker reviewer-a --brief brief.md
✓ 완료 · 리뷰 4건 (3.2s)
$ echo $?
0
✕ 디스패처가 reviewer-a 를 호출한 적이 없습니다
✕ 그 출력은 이름이 비슷한 다른 경로가 만든 것입니다
종료코드 0만으로 의도한 일이 정확히 끝났다고 할 수 없다
위 세 줄은 전부 사실이다. 아래 두 줄도 전부 사실이다. 문제는 위 세 줄만 보고 아래 두 줄을 없는 것으로 취급했다는 데 있다.

종료코드가 말하지 않는 것

이 책은 처음부터 끝까지 한 문장을 붙들고 간다: CLI의 종료코드 0은 그 프로그램이 성공으로 분류했다는 뜻이다. 의도한 작업이 정확히 끝났는지는 별도 증거로 확인한다.

종료코드는 프로세스 계약이다. 어떤 조건을 성공으로 취급하는지는 프로그램마다 다르다. 오류를 삼키고 0을 반환할 수도 있으므로 인증 성공이나 요청 전송까지 값 하나로 단정할 수 없다. 그 이상을 읽어내는 순간 사고가 난다. 구체적으로 종료코드 0과 비어있지 않은 표준출력이 보장하지 않는 것들:

  • 내가 의도한 모델·백엔드가 실제로 요청을 받았는지 (설정에만 이름이 있고 실제 경로는 다른 곳으로 샜을 수 있다)
  • 실행 중에 내가 준 입력(브리프·소스)을 실제로 열어봤는지 (프롬프트만 보고 그럴듯한 답을 지어냈을 수 있다 — 이 이야기는 7장에서 정면으로 다룬다)
  • 실행이 내가 걸어둔 권한·범위 제약 안에서 돌았는지 (권한이 새서 의도 밖의 것을 건드렸을 수 있다)
  • 응답이 독립적으로 재검산됐는지 (구조 검사는 모양만 본다 — 헤더가 있는지, 파싱되는지. 내용이 맞는지는 안 본다)
  • 결과가 최종적으로 채택됐는지 (검증을 통과해도 다른 워커의 상충하는 결과에 밀려 실제로는 안 쓰였을 수 있다)

"동작했다"는 말은 이 다섯 가지 질문 중 정확히 몇 번째까지 답한 말인지를 명시하지 않으면 아무 의미가 없다. 이 책에서는 이 질문들을 설치·등록·노출·사전점검·실행·검증·수용의 일곱 단계에 나눠 담는다.

증거의 사다리

증거에는 등급이 있다. 아래 표에서 번호가 클수록 더 많은 확인을 요구한다. 높은 번호를 주장하려면 앞 단계의 증거도 갖춰야 한다. 앞 단계만 확인한 상태에서 뒤 단계까지 확인했다고 말하면 안 된다.

01설치됨파일이 거기 있다
02등록됨설정에 이름이 있다
03도구로 노출됨부를 수 있다
04사전점검 통과보낼 준비가 됐다
05실행 영수증 통과돌긴 돌았다 — 여기서 멈춘다
06결과 검증됨내용이 맞다
07수용됨여기가 완료다
대부분의 파이프라인은 05에서 멈춰 있으면서 그것을 완료라고 부른다. 돌았다는 것과 결과가 맞다는 것은 다르다. 아래 표가 각 칸이 보장하는 것과 보장하지 않는 것이다.
단계 무엇을 보장하는가 무엇을 보장하지 않는가
① 설치됨 (INSTALLED_STATIC) 실행 파일·패키지가 디스크에 존재한다 등록조차 안 됐을 수 있다. 버전이 안 맞을 수 있다
② 등록됨 (REGISTERED) 설정에 이름과 경로가 올라 있다 아무도 그 이름을 실제로 호출한 적이 없을 수 있다
③ 도구로 노출됨 (TOOL_EXPOSED) 호출자가 그 이름으로 호출을 시도할 스키마·핸들이 생겼다 그 핸들 뒤에 유효한 실행 경로가 붙어 있는지는 모른다
④ 디스패치 사전점검 통과 (DISPATCH_PREFLIGHT_PASS) 정책·권한·경로가 사전조건을 만족해 호출이 허가됐다 그 허가로 실제 실행까지 이어졌는지는 아직 모른다
⑤ 실행 영수증 통과 (OPERATION_RECEIPT_PASS) 프로세스가 실제로 실행되어 응답을 반환했고, 어떤 입력·권한으로 돌았는지가 기록·검증됐다 그 응답의 내용이 맞는지, 작업을 실제로 다뤘는지는 모른다
⑥ 결과 검증됨 (RESULT_VERIFIED) 응답 내용이 독립적으로 재검산되어 요구한 형식·근거를 갖췄다고 확인됐다 그 결과가 최종적으로 다른 작업의 입력이 될 자격까지 얻었는지는 모른다 (상충하는 결과가 있을 수 있다)
⑦ 수용됨 (FAN_IN_ACCEPTED) 통합 권한을 가진 쪽이 그 결과를 실제 의사결정에 반영했다 — (이게 종착점이다)

앞서 본 사고를 이 표에 대 보면 정확히 짚인다. 그 워커는 ①②까지는 사실이었다(파일도 있었고 이름도 등록돼 있었다). ③도 사실이었다(스키마가 노출돼 호출 시도는 가능했다). 그런데 실제 호출은 ④를 거치지 않고 다른 경로로 새 나갔다. 로그는 ⑤⑥을 주장했지만 그 ⑤⑥의 실체는 애초에 부르려던 자리의 것이 아니었다. 낮은 단계의 사실들을 근거로 높은 단계를 참칭한 것, 이 사다리가 막으려는 실수가 바로 이것이다. 그래서 규칙은 간단하다 — 이전 단계를 나중 단계인 척 재명명할 수 없다.

사다리도 옆으로 샌다

사다리를 정의했다고 사고가 끝나지는 않는다. 실제로 이 사다리를 도입한 뒤에도 옆으로 새는 경로가 세 가지 더 나왔다.

1사람이 한 번 쳐본 것을 실행 영수증으로
사람의 손은 기껏해야 ④ 근처의 예비 점검이다. 인자 조립도, 권한 프로필도, 재시도 로직도 자동 경로와 전부 다르다
2형식 통과를 내용 검증으로
JSON 이 파싱되고 헤더가 있으면 통과다. 완벽하게 그럴듯하고 완전히 틀린 응답도 같이 통과한다
3계약이 바뀌었는데 옛 영수증을 재사용
발급 당시엔 정당했다. 새 요구조건을 애초에 만족할 수 없는 낡은 것일 뿐이다. 시점 없는 영수증은 영원히 유효해 보인다
세 경우 모두 "급하니까 이번만"이라는 예외였다. 사다리는 예외를 허용하지 않을 때만 사다리다.

직접 스모크 테스트를 실행 영수증으로 착각. 사람이 터미널에서 직접 CLI를 한 번 쳐보고 "된다"를 확인한 뒤, 그 확인을 근거로 자동화 경로도 됐다고 로그에 적은 적이 있다. 사람 손으로 한 번 확인해 봤자 기껏해야 ④ 근처의 예비 점검이다. 디스패처가 실제로 그 요청을 처리했다는 ⑤의 증거가 되지는 않는다. 사람이 됐다고 자동 경로도 되는 게 아니다 — 인자 조립 방식도, 권한 프로필도, 실패 시 재시도 로직도 전부 다르다.

구조 검증기 통과를 내용 검증으로 착각. 응답이 JSON으로 파싱되고 필수 헤더가 다 있으면 구조 검증기는 통과 판정을 낸다. 이건 ⑤와 ⑥ 사이 어딘가의 "형식은 맞다"는 확인에 그친다. ⑥이 요구하는 "내용이 맞다"는 확인은 빠져 있다. 형식만 보고 "검증됐다"고 적는 순간, 누가 봐도 그럴듯하지만 완전히 틀린 응답도 통과한다.

계약이 바뀌었는데 오래된 영수증을 재사용. 한 번은 검증 계약을 강화한 직후, 강화 전 라운드에서 만든 영수증이 새 게이트를 그대로 통과한 적이 있다. 그 영수증은 발급될 당시엔 정당했다. 하지만 새로 추가된 요구조건(예: 특정 필드, 특정 검증 단계)을 애초에 만족할 수 없는 낡은 것이었다. 아무도 "이 영수증은 옛 계약 것이니 무효"라고 도장을 찍지 않았을 뿐이다. 시점을 적어 두지 않은 영수증은 영원히 유효한 영수증처럼 다뤄지기 쉽다.

세 경우 모두 급하니까 이번만이라는 예외였다. 사다리는 예외를 허용하지 않을 때만 사다리다. 한 칸이라도 "이번엔 건너뛰어도 되지" 하고 넘어가면 다음 사람은 건너뛴 자리가 원래 있던 자리인 줄 안다.

최소 검증기

아래는 영수증(JSON)의 필수 필드와 기본 값 제약을 확인하는 최소 구현이다. 파일 존재·실행 사실·권한·검증자 신원 자체는 신뢰된 실행기가 별도로 확인해야 한다. 입력 JSON을 만든 사람이 거짓말하지 않았다는 사실까지 이 코드가 증명하지는 않는다. 이 구현은 두 가지를 지킨다 — 높은 단계를 주장하려면 그보다 낮은 모든 단계의 필드가 이미 채워져 있어야 한다. 검증자가 실행 주체 자신이면 독립 검증으로 세지 않는다.

이 파일은 tools/verify_operation_ladder.py에 둔다.

#!/usr/bin/env python3
"""증거 사다리 7단계를 영수증(JSON) 하나로 강제하는 최소 검증기."""
from __future__ import annotations

import json
import re
from datetime import datetime
import sys
from pathlib import Path

LADDER = [
    "INSTALLED_STATIC",
    "REGISTERED",
    "TOOL_EXPOSED",
    "DISPATCH_PREFLIGHT_PASS",
    "OPERATION_RECEIPT_PASS",
    "RESULT_VERIFIED",
    "FAN_IN_ACCEPTED",
]

# 각 단계는 그 아래 모든 단계의 필드를 포함한다 — 건너뛴 단계가 있으면 안 되기 때문이다.
REQUIRED_FIELDS = {
    "INSTALLED_STATIC": {"executable_path"},
    "REGISTERED": {"executable_path", "registered_name"},
    "TOOL_EXPOSED": {"executable_path", "registered_name", "call_schema"},
    "DISPATCH_PREFLIGHT_PASS": {
        "executable_path", "registered_name", "call_schema", "preflight_policy_id",
    },
    "OPERATION_RECEIPT_PASS": {
        "executable_path", "registered_name", "call_schema", "preflight_policy_id",
        "process_exit_code", "process_stdout_nonempty", "actual_input_hash",
    },
    "RESULT_VERIFIED": {
        "executable_path", "registered_name", "call_schema", "preflight_policy_id",
        "process_exit_code", "process_stdout_nonempty", "actual_input_hash",
        "independent_verifier_id", "independent_verifier_verdict",
    },
    "FAN_IN_ACCEPTED": {
        "executable_path", "registered_name", "call_schema", "preflight_policy_id",
        "process_exit_code", "process_stdout_nonempty", "actual_input_hash",
        "independent_verifier_id", "independent_verifier_verdict",
        "accepted_by", "accepted_at",
    },
}


def verify_receipt(receipt: dict) -> tuple[bool, str]:
    if not isinstance(receipt, dict):
        return False, "영수증은 JSON 객체여야 한다"
    claimed = receipt.get("stage")
    if claimed not in LADDER:
        return False, f"알 수 없는 단계 이름: {claimed!r}"

    missing = REQUIRED_FIELDS[claimed] - receipt.keys()
    if missing:
        return False, (
            f"'{claimed}' 단계를 주장하려면 이전 단계들의 필드까지 모두 있어야 한다. "
            f"빠진 필드: {sorted(missing)}"
        )

    rank = LADDER.index(claimed)
    for field in REQUIRED_FIELDS[claimed] - {"process_exit_code", "process_stdout_nonempty", "call_schema"}:
        value = receipt[field]
        if not isinstance(value, str) or not value.strip():
            return False, f"비어 있거나 문자열이 아닌 필드: {field}"
    if rank >= 2 and not isinstance(receipt["call_schema"], dict):
        return False, "call_schema는 비어 있지 않은 객체여야 한다"
    if rank >= 2 and not receipt["call_schema"]:
        return False, "call_schema가 비어 있다"
    if rank >= 4:
        code = receipt["process_exit_code"]
        if type(code) is not int or code != 0:
            return False, "이 계약은 정수 종료코드 0을 요구한다"
        if receipt["process_stdout_nonempty"] is not True:
            return False, "이 계약은 비어 있지 않은 출력을 요구한다"
        if not re.fullmatch(r"[0-9a-f]{64}", receipt["actual_input_hash"]):
            return False, "입력 SHA256 형식 오류"
    if rank >= 5:
        if receipt["independent_verifier_id"].strip().casefold() == receipt["registered_name"].strip().casefold():
            return False, "검증자가 실행 주체 자신이면 독립 검증이 아니다"
        if receipt["independent_verifier_verdict"] != "PASS":
            return False, "독립 검증 판정이 PASS가 아니다"
    if rank >= 6:
        try:
            accepted = datetime.fromisoformat(receipt["accepted_at"].replace("Z", "+00:00"))
            if accepted.tzinfo is None:
                raise ValueError("timezone missing")
        except ValueError:
            return False, "accepted_at은 시간대가 있는 ISO 8601 시각이어야 한다"

    return True, f"'{claimed}' 단계까지 유효"


if __name__ == "__main__":
    receipt = json.loads(Path(sys.argv[1]).read_text(encoding="utf-8"))
    ok, message = verify_receipt(receipt)
    print(message)
    sys.exit(0 if ok else 1)

이 검증기는 필드 누락, 실패 종료코드, 빈 출력, 검증 FAIL, 실행자와 같은 검증자 식별자를 거부한다. 값만 그럴듯하게 꾸민 영수증은 통과할 수 있다. 실제 파일·프로세스·검증 결과와 연결하는 절차 및 계약 버전·발급 시각 검사는 운영 파이프라인의 별도 책임이다. 필수 필드를 추가하면 그 필드가 없는 옛 영수증은 거부하지만, 시점만 오래된 영수증까지 자동으로 찾아내지는 않는다.

스스로 빨간불을 켜보기

가드는 통과만 시켜보면 검증한 게 아니다. 일부러 깨뜨려서 빨간불이 켜지는지 봐야 검증한 것이다. 자기 파이프라인에 다음 네 가지를 직접 걸어보라.

  1. 설치만 되고 등록은 안 된 상태를 만들어라 (설정 파일에서 그 이름을 지운다). 파이프라인이 그걸 "등록됨"이라 부르는지 확인한다 — 부르지 않아야 정상이다.
  2. 등록은 됐지만 실제 실행 경로는 끊긴 상태를 만들어라 (디스패처가 그 이름을 다른 곳으로 우회하게 하거나, 실행 파일 권한을 지운다). 그런데도 로그가 "실행됨"을 찍는지 확인한다 — 찍으면 그 로그는 못 믿는다.
  3. 실행은 됐지만 검증 단계를 강제로 건너뛰게 하고, RESULT_VERIFIED가 여전히 찍히는지 확인한다.
  4. REQUIRED_FIELDS에 필드를 하나 추가해 계약을 강화한 뒤, 강화 이전에 만들어둔 영수증 파일을 그대로 다시 넣어봐라. 위 검증기라면 즉시 거부해야 정상이다.

넷 중 하나라도 빨간불이 안 켜지면 그 칸은 "통과"가 아니라 "한 번도 실행된 적 없는 검사"다. 이 책의 나머지 장들에서도 — 특히 위임을 다루는 6장과 7장에서 — 매번 이 사다리를 놓고 "어느 칸까지 실제로 올라갔는지"를 묻는다.
