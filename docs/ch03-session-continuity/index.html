3장 — 세션이 끊겨도 이어지게

기술 검증판 2026-09-28 · 원고 최종 수정 2026-10-02

증상
세션이 끊기면 다음 세션이 이미 기각한 설계안을 다시 제안한다
원인
이전 대화를 이어받지 않은 새 세션에는 작업 판단을 다시 전달해야 한다
붙일 장치
SESSION.md 한 장 — 목표·현재 상태·다음 단계·결정 기록·파일 흔적
그래도 부족했던 것
파일 하나로는 구멍이 셋 남는다. 그 셋을 메우는 것이 이 장 후반이다

증상

금요일 저녁에 세션을 닫았다. 월요일 아침에 새 세션을 열어 "지난주 하던 것 이어서 해줘"라고 말했다. 에이전트는 저장소를 다시 스캔하고 지난주에 이미 검토하고 기각한 설계안을 다시 제안했다. 이미 "이 방식은 동시성 문제가 있어서 안 쓰기로 했다"고 결론 낸 접근을, 아무 일도 없었다는 듯 다시 꺼내 왔다.

더 나쁜 경우도 있었다. 컨텍스트 한도에 걸려 세션이 중간에 끊겼다. 다음 세션은 그 전 세션이 어디까지 했는지 전혀 모르는 채로 시작했고, 이미 고친 버그를 "발견"하고 다시 고치려다 git diff와 충돌했다. 30분을 들여서야 "아, 이건 이미 지난 세션에서 끝난 일이구나"를 깨달았다.

두 경우 다 이전 대화를 이어받지 않은 새 세션에서 인계 정보가 부족했다. Claude Code는 대화를 로컬에 저장하므로 --continue나 --resume으로 이어갈 수 있다. 그러나 새 세션에 과거 대화 전체가 자동으로 전달되는 것은 아니다. 코드 diff는 "무엇이 바뀌었는가"는 보여줘도 "왜 그렇게 바꿨는가"와 "무엇을 시도했다가 버렸는가"는 보여주지 않는다.

왜 그런가

우리는 은연중에 "대화 자체가 기억"이라고 가정하고 일했다. 방금 논의한 내용은 당연히 다음 지시에도 살아있을 거라고 여긴다. 같은 세션 안에서는 맞는 가정이다. 그런데 세션은 영원하지 않다 — 컨텍스트 한도든, 사용자가 직접 닫는 경우든, 며칠 뒤 재개하는 경우든 그 가정은 깨진다. 저장된 대화를 재개할 수는 있어도 새 세션이 그 내용을 모두 읽었다고 가정할 수는 없다. 자동 메모리도 설정·저장 범위에 따라 달라진다.

명시적인 인계 파일은 재개 기능을 쓸 수 없거나 다른 도구로 옮겨갈 때도 유용하다. 그런데 코드 diff와 커밋 메시지는 "결과"를 기록하지 "과정"을 기록하지 않는다. 왜 이 방법을 버렸는지, 다음에 뭘 해야 하는지는 diff에 없다. 그 정보를 남기는 전용 파일이 없으면 다음 세션은 매번 코드를 거꾸로 읽어서 의도를 추측해야 한다 — 느리고 틀리기 쉽다.

최소 해법 — SESSION.md 한 장

가장 단순한 해법은 파일 하나다. 작업 폴더 루트에 SESSION.md를 둔다. 다음 세션이 다른 어떤 작업보다 먼저 읽는 문서는 이 파일 하나로 정한다. 처음엔 이렇게 짧아도 된다.

~/project/SESSION.md:

# SESSION — 세션 이어가기 기록

## 목표
(첫 세션 마감 때 채운다)

## 현재 상태
(아직 기록 없음)

## 다음 단계
1. (아직 기록 없음)

## 결정 기록

## 파일 흔적

"먼저 읽는다"는 규율을 사람의 기억력에 맡기지 않으려고 세션을 열 때 돌리는 짧은 스크립트를 하나 곁들인다. 파일이 없으면 템플릿으로 만들고, 있으면 핵심 세 섹션만 요약해 화면에 띄운다.

~/project/tools/session_open.py:

#!/usr/bin/env python3
"""세션 시작 의식 — SESSION.md 핵심 섹션을 출력한다.
출력은 모델이 읽거나 따랐다는 증거가 아니다. 없으면 템플릿에서 만든다.

사용: python3 tools/session_open.py [SESSION.md 경로]
"""
from __future__ import annotations

import re
import sys
from pathlib import Path

TEMPLATE = """# SESSION — 세션 이어가기 기록

## 목표
(첫 세션 마감 때 채운다)

## 현재 상태
(아직 기록 없음)

## 다음 단계
1. (아직 기록 없음)

## 결정 기록

## 파일 흔적
"""


def extract_section(text: str, name: str) -> str:
    text = re.sub(r"<!--.*?-->", "", text, flags=re.S)
    m = re.search(rf"^## {re.escape(name)}\n(.*?)(?=\n## |\Z)", text, flags=re.S | re.M)
    return m.group(1).strip() if m else "(섹션 없음)"


def main() -> int:
    path = Path(sys.argv[1] if len(sys.argv) > 1 else "SESSION.md")
    if not path.is_file():
        path.write_text(TEMPLATE, encoding="utf-8")
        print(f"[생성] {path} — 템플릿으로 새로 만들었습니다. 첫 세션 마감 때 채우세요.")
        return 0
    text = path.read_text(encoding="utf-8")
    print(f"=== {path} 재정박 요약 ===")
    print("\n[목표]\n" + extract_section(text, "목표"))
    print("\n[현재 상태]\n" + extract_section(text, "현재 상태"))
    next_steps = extract_section(text, "다음 단계")
    first_line = next((ln for ln in next_steps.splitlines() if ln.strip()), "(없음)")
    print("\n[다음 단계 — 첫 항목]\n" + first_line)
    return 0


if __name__ == "__main__":
    sys.exit(main())

이걸 돌리면 다음 세션은 코드를 뒤지기 전에 "지금 무슨 작업 중이고 뭘 먼저 해야 하는지"를 3초 안에 안다. 이 상태로도 1절의 첫 번째 사고 — 기각한 설계를 다시 꺼내는 것 — 는 많이 줄어든다. 결정 기록에 "이 방식은 버렸다"고 적혀 있으면 그 설계는 다시 안 꺼낸다.

그걸로 부족했던 지점

파일 하나로는 세 가지 구멍이 그대로 남는다.

(a) 통째로 다시 쓸수록 세부가 조금씩 빠진다. 세션을 마감할 때마다 "깔끔하게 정리해서 다시 쓰자"는 유혹이 생긴다. 그런데 파일 전체를 다시 쓰면 이번엔 안 중요해 보였던 디테일을 지운다. 다음번엔 그 디테일이 결정적일 수 있다는 걸 그때는 모른다. 세 번 재작성하면 세 번 다 "이번엔 안 중요해 보인 것"이 달라서 결국 아무것도 안전하게 남지 않는다. 섹션마다 갱신 규칙을 달리 정해야 한다 — 목표는 건드리지 않고 스냅샷은 덮어쓰고, 기록은 추가만 한다.

(b) 마감 신호 없이 끊기면 '현재 상태'가 낡은 채 방치된다. 컨텍스트 한도, 강제 종료, 네트워크 문제 — 세션은 종종 "마감"이라는 절차 없이 그냥 끊긴다. 그러면 SESSION.md의 '현재 상태'는 마지막으로 제대로 갱신한 시점에 멈춘 채 남는다. 다음 세션이 그걸 실물과 대조하지 않고 그대로 믿으면 이미 끝난 일을 다시 하거나 이미 버린 접근을 다시 시도한다. 사람이 이런 방치를 매번 알아챈다는 보장이 없으니 커밋 이력과 대조해 "이 파일은 한동안 안 건드렸다"는 신호를 스크립트가 대신 내야 한다.

(c) 경로를 산문에 녹여 두면 다음 세션이 그걸 또 찾아 헤맨다. "결제 모듈의 재시도 로직을 고쳤다"라고만 적으면 다음 세션은 결제 모듈 안에서 재시도 로직을 다시 검색해야 한다. 파일 경로·함수명·에러 메시지는 검색 가능한 리터럴로 그대로 박아야 한다 — payments/gateway.py의 retry_charge()처럼. 산문으로 녹이는 순간 그 정보는 흐릿한 단서가 된다. 텍스트 유사도 검색으로만 걸리고 정확히 그 식별자를 아는 사람만 빠르게 찾을 수 있다.

이 세 문제는 전부 "섹션마다 규칙이 다르다"는 설계 하나로 푼다. 목표는 이 폴더가 왜 있는지 합의한 내용이고 프로젝트 도중 거의 안 바뀐다 — 그래서 고정한다. 현재 상태와 다음 단계는 시시각각 바뀌는 스냅샷이다. 낡은 스냅샷은 새 스냅샷으로 통째로 갈아 끼워야 한다 — 그래서 덮어쓴다. 결정 기록과 파일 흔적은 역사다 — 역사는 삭제하면 안 된다. 뒤집힌 결정도 지우지 않고 "뒤집혔다"고 한 줄 더 쌓아야 한다. 섹션마다 담는 정보의 성격이 다르니 규칙도 섹션마다 다르다. 고정 정보를 덮어쓰면 맥락을 잃고 스냅샷을 추가만 하면 최신 상태를 못 찾는다. 역사를 덮어쓰면 "왜 그렇게 안 했는가"라는 물음의 답이 사라진다.

뒤집힌 결정을 지우지 않는 규율은 특히 값지다. "재시도 정책을 지수 백오프로 바꿨다"고 기록해뒀는데 두 세션 뒤에 다시 고정 간격으로 되돌렸다면, 그 기록을 지우고 새 결정만 남기고 싶은 유혹이 생긴다. 그러면 다음 세션은 왜 예전에 지수 백오프를 썼었는지, 그리고 왜 다시 버렸는지를 영영 모른다. "2026-08-01 지수 백오프 결정을 되돌림(사유: 트래픽 급증 시 응답 지연 누적 관측)"처럼 뒤집힌 사실 자체를 새 줄로 쌓으면 세 번째 세션이 같은 삽질을 또 반복하는 걸 막는다.

~/project/tools/session_stale_check.py:

#!/usr/bin/env python3
"""SESSION.md 방치 감지기.

마감 신호 없이 세션이 끊기면 '현재 상태'가 낡은 채로 방치될 수 있다. 이 스크립트는
정답을 판정하지 않는다 — SESSION.md를 건드리지 않은 채 커밋이 N개 이상 쌓였다는
사실만 알린다. 최종 판단(낡았는지 아닌지)은 사람이 한다.

사용: python3 tools/session_stale_check.py [--threshold N] [SESSION.md 경로]
"""
from __future__ import annotations

import argparse
import subprocess
import sys
from pathlib import Path


def run(*args: str) -> str:
    return subprocess.run(args, capture_output=True, text=True, check=True).stdout.strip()


def main() -> int:
    ap = argparse.ArgumentParser()
    ap.add_argument("path", nargs="?", default="SESSION.md")
    ap.add_argument("--threshold", type=int, default=5)
    args = ap.parse_args()

    path = Path(args.path)
    if not path.is_file():
        print(f"[INFO] {path} 없음 — 아직 세션 인계 파일을 안 쓰는 폴더입니다.")
        return 0

    last = run("git", "log", "-1", "--format=%H", "--", str(path))
    if not last:
        print(f"[INFO] {path} 이 아직 커밋되지 않았습니다.")
        return 0

    since = run("git", "rev-list", "--count", f"{last}..HEAD")
    n = int(since)
    if n >= args.threshold:
        print(f"[WARN] {path} 갱신 이후 커밋 {n}개 — 마감 신호 없이 세션이 끊겼을 가능성. "
              f"'현재 상태'를 실물과 대조하세요.")
        return 1
    print(f"[OK] {path} 갱신 이후 커밋 {n}개 (임계 {args.threshold})")
    return 0


if __name__ == "__main__":
    sys.exit(main())

이 검사기는 커밋 기준 신선도만 본다. 아직 커밋하지 않은 최신 수정, 실제 내용의 정확성, 다른 브랜치의 상태는 판정하지 않는다. 실제 저장소가 아닌 임시 저장소에서 아래 커밋 실습을 한다.

세션 시작 스크립트(session_open.py)는 2절과 같다 — 최종형에서 바뀌는 건 파일 구조뿐, 여는 절차는 그대로다.

직접 확인하는 법

1. 재정박이 실제로 3초 요약을 내는지. 위 "채워진 예시"를 SESSION.md로 저장하고 python3 tools/session_open.py를 돌린다. 목표·현재 상태·다음 단계 첫 항목이 화면에 바로 뜨는지 본다. 여기서 아무것도 안 뜨거나 엉뚱한 섹션이 섞이면 정규식이 실제 파일의 헤더 표기와 안 맞는다 — 이 스크립트를 프로젝트에 맞출 때는 정규식부터 깨진다.

2. 인계 파일을 갱신하지 않은 상태를 만든다 — 경고 확인. 로컬 git 저장소에서 SESSION.md를 커밋한 뒤, 그 파일은 건드리지 않고 무관한 커밋을 5개 이상 쌓는다.

$ git add SESSION.md && git commit -q -m "session update"
$ for i in 1 2 3 4 5; do echo "x" >> notes.txt; git add notes.txt; git commit -q -m "unrelated $i"; done
$ python3 tools/session_stale_check.py
[WARN] SESSION.md 갱신 이후 커밋 5개 — 마감 신호 없이 세션이 끊겼을 가능성. '현재 상태'를 실물과 대조하세요.

WARN이 안 뜨면 임계값이 너무 높거나 git log -- <경로>가 프로젝트의 실제 파일 위치와 안 맞는다. 반대로 SESSION.md를 갱신하는 커밋을 하나 더 하면 카운터가 0으로 돌아오는지도 확인한다 — 리셋되지 않으면 마지막 커밋 해시를 잘못 잡고 있다.

3. 섹션 갱신 규칙을 스스로 어겨 본다. 마감할 때 '결정 기록'을 지우고 새로 쓰거나 '현재 상태'에 세 문단짜리 서술을 쌓아본다. 다음 세션 시작 때 그 파일만 읽고 "과거에 어떤 접근을 버렸는지"를 답할 수 있는지 스스로 확인한다. 답을 못 하면 규칙을 어긴 것이니 그 즉시 파일을 정정한다 — 지우지 않고 "YYYY-MM-DD 이전 기록 일부 누락 확인, 이하 복원"처럼 사실을 남겨 복구한다.

4. 최종 자체 점검. 세션을 마감할 때마다 스스로 묻는다 — "다음 세션이 이 파일만 읽고 '다음 할 일'과 '건드린 파일'을 말할 수 있나?" 대답이 "아니오"면 아직 마감이 끝난 게 아니다. 이 장 전체가 이 질문 하나를 위해 있다 — SESSION.md의 목적은 사람을 위한 회고록이 아니다. 다음 세션이 그것만 읽고 바로 일을 시작할 수 있게 하는 인계 문서다.

대화 재개 근거: Claude Code common workflows, 확인 2026-09-28. SESSION.md는 이 책에서 정한 인계 방식이며 제품이 자동 관리하는 예약 파일명이 아니다.
