4장 — 직접 할까 위임할까

기술 검증판 2026-09-28 · 원고 최종 수정 2026-10-03

증상
직접 5분이면 될 일을 위임했다가 15분짜리 왕복이 됐다
원인
위임에는 고정비가 있다. 새 컨텍스트 구축·브리프 작성·결과 검토
붙일 장치
물량·명세 확정도·병렬성으로 직접/위임을 가르는 판정 함수
그래도 부족했던 것
명세가 모호한데 물량만 보고 위임하면, 이 판정에서 가장 비싼 실수가 난다

파일 세 개짜리 버그를 고쳐야 했다. 재현 조건은 이미 파악했고 고칠 함수도 특정해뒀다. "이 정도면 서브에이전트한테 맡기고 나는 다른 걸 보자"는 생각으로 브리프를 썼다. 브리프를 쓰는 데 3분, 에이전트가 새 컨텍스트를 구축하고 코드베이스를 다시 읽는 데 또 몇 분, 결과가 돌아온 뒤 검토하는 데 2분. 직접 고쳤으면 5분 안에 끝났을 일이 15분짜리 왕복이 됐다.

반대 방향의 실수도 있었다. 저장소 전체에서 오래된 API 호출 패턴 80곳을 새 시그니처로 바꾸는 작업이었다. "패턴이 뻔하니까 내가 직접 하지" 하고 붙잡았다가, 파일을 스무 개쯤 열었을 때 세션 컨텍스트가 꽉 차서 압축이 걸렸고, 압축된 대화에서 어느 파일을 이미 고쳤는지 헷갈리기 시작했다.

두 실수 모두 "직접 할지 위임할지"를 그때그때 감으로 정했다. 그리고 감은 대개 틀렸다. 한 번은 위임하면 안 될 걸 위임했고, 한 번은 위임했어야 할 걸 붙잡고 있었다. 더 근본적인 문제는 위임을 결정한 뒤에 벌어졌다. "위임하는 김에 이번엔 좀 더 강하게 시켜야지" 하고 에이전트의 effort를 올리려고 했는데 그런 다이얼이 애초에 없었다. 존재하지 않는 선택지를 붙잡고 몇 분을 허비한 뒤에야, 내가 직접 실행할 때와 위임할 때를 같은 종류의 결정으로 착각하고 있었다는 걸 깨달았다.

왜 그런가

DIRECT와 DELEGATE는 대칭이 아니다

이 장의 판정기는 모델·effort가 고정된 워커 풀, 경제형 워커 없음이라는 저자의 운영 구성을 예로 든다. Claude Code 전체의 제약이 아니다. 현재 공식 문서에는 서브에이전트의 model·effort 설정과 세션 값 상속이 있다. 먼저 사용하는 런타임의 실제 선택지를 확인해야 한다.

직접 실행(DIRECT)과 위임(DELEGATE)은 언뜻 "누가 하느냐"의 차이로만 보인다. 실제로는 고를 수 있는 것의 종류 자체가 다르다.

명세가 확정됐나아니면 여기서 멈춘다

직접 실행위임 고정비가 산출물보다 크다
순서가 중요하다. 물량을 먼저 보면 안 된다. 명세가 모호한 채로 물량만 보고 위임하면, 위임받은 쪽이 불확실한 목표를 놓고 탐색하다 엉뚱한 결과를 들고 온다.
실제로 고르는 것 사다리가 실재하는가
위임 어느 워커·역할이 지금 구성에 맞는가 — 그뿐이다 아니다. 모델·effort는 워커의 고정된 속성이다. 위임 대상을 정하는 도구는 그 값을 바꾸지 않는다.
직접 실행 내 세션의 모델과 effort 그렇다. /model과 /effort로 조작하는 실제 2축 사다리가 있다.

이 예제에서 위임 워커의 모델·effort는 배차 설정 파일에 미리 박혀 있는 값이다. "이번엔 위임하되 effort를 max로 올려서 시키자"는 말은 성립하지 않는다. 그 워커는 애초에 그 effort로만 뛴다. 반대로 직접 실행에서는 effort와 모델을 내가 그때그때 바꿀 수 있다.

이 비대칭을 모르면 두 가지 헛수고를 한다. 하나는 위임 워커에게 없는 다이얼을 찾아 설정 화면을 뒤지는 것(내가 겪은 것), 다른 하나는 반대로 직접 실행 중에 "이 작업은 그냥 다른 워커를 붙이면 되지 않나" 하며 존재하지 않는 위임 경로를 찾는 것이다. 판정을 시작하기 전에는 "어느 쪽이 나은가"를 따지지 말고 "지금 내가 조작할 수 있는 축이 무엇인가"부터 물어야 한다. 위임을 택했다면 남은 선택은 워커 하나뿐이고, 직접을 택했다면 남은 선택은 모델과 effort 두 개다.

"위임하면 싸진다"는 착각

위임이 항상 더 싸다는 직관은 매력적이다. 하지만 이 직관을 따르면 두 가지를 놓친다.

첫째, 새 컨텍스트로 시작하는 일반 서브에이전트에는 컨텍스트 구축 비용이 붙는다. 다만 현재 Claude Code의 fork 방식은 부모 대화와 프롬프트 캐시를 공유할 수 있다. 모든 위임이 캐시를 새로 만든다고 계산하면 틀린다. 전달받은 컨텍스트에 필요한 정보가 없으면 위임받은 쪽이 코드베이스와 프로젝트 관례를 다시 읽어야 한다.

둘째, 명세를 쓰는 데도 토큰이 든다. 위임하려면 목표·범위·완료조건·검증 방법을 텍스트로 정리해서 건네야 한다. 이 브리프 작성 비용은 공짜가 아니다. 명세가 부실하면 위임받은 쪽이 엉뚱한 걸 만들고 명세를 정성껏 쓰면 거기에 시간과 토큰이 들어간다.

이 두 고정비를 치를 만한 이득이 있는지 따져야 한다. 대량 작업은 그 후보지만 독립 검토나 특화 도구 접근처럼 물량 외의 이유도 있다. 파일 몇 개짜리 단발 구현, 한 번 쓰고 버릴 스크립트, 이미 원인을 아는 버그 수정 — 이런 일은 위임 고정비가 이득보다 클 수 있다. 반대로 파일 수십 개에 걸친 일괄 치환, 반복되는 변환 작업, 병렬로 쪼갤 수 있는 테스트 작성처럼 반복 작업에서는 병렬 처리로 시간을 줄일 가능성이 있다.

더 나쁜 경우도 있다. 물량이 많아서 "이건 위임감이다" 판단했는데 위임 워커 풀에 애초에 경제형(더 저렴한) 로드아웃이 없는 경우다. 위임 워커가 전부 프리미엄급으로 고정돼 있다면 위임해도 티어가 내려가지 않는다. 이런 상황에서도 위임으로 병렬성과 메인 컨텍스트 보존을 얻을 수 있다. 비용 절감 여부는 토큰 사용량·캐시·실행시간을 실제로 재야 한다. 반대로 세션을 낮은 티어로 직접 전환하는 쪽이 비용상 유리할 수 있다. 세션 모델을 바꾸면 기존 캐시를 그대로 쓰지 못할 수 있어 전환 비용도 확인해야 한다. 그래서 정직한 결론은 하나뿐이다. 직접-위임 쌍을 나란히 측정한 실측치가 없으면 비용을 비교할 때 "측정되지 않음"이라고 말해야 한다. "위임하면 37% 싸진다" 같은 숫자는 근거 없이 지어낸 것이다.

최적화 목표가 없으면 판정 자체가 성립하지 않는다

앞 절의 결론을 뒤집어보면 이렇다. 물량이 많고 명세가 확정됐고 독립적으로 쪼개지는 작업인데, 위임 워커 풀에 경제형이 없다면 — 직접과 위임 중 어느 쪽이 나은지는 그 작업만 봐서는 알 수 없다. 이 예제 정책은 비용이 최우선이면 직접 실행, 완료 시간이나 메인 컨텍스트 보존이 최우선이면 위임을 후보로 낸다. 실제 이득은 측정해야 한다. 조건이 같아도 답은 갈린다. 판정을 계속하려면 "무엇을 최적화하고 싶은가"를 먼저 알아야 한다.

이걸 모르는 채로 라우터가 답을 하나 골라버리면 그건 판정이 아니라 도박이다. 그래서 이런 경우 판정기는 반드시 NEEDS_PREFERENCE를 반환하도록 설계했다. 답을 지어내는 대신 "비용 / 완료시간 / 메인 컨텍스트 보존 중 무엇이 우선입니까"라고 되묻는다. 정보가 부족한 상태에서 확신에 찬 답을 내놓기보다 판정을 멈추고 되묻는 편이 훨씬 정직하다.

최소 해법

가장 단순한 버전은 대략 이렇다. 축 하나(물량)만 보고 갈림길을 정한다.

이 파일은 예시로 어디에나 둘 수 있다. 여기서는 편의상 naive_gate.py로 부른다.

#!/usr/bin/env python3
"""최소 해법 — 물량 하나만 보고 정한다. 구멍이 있다."""


def naive_gate(axes: dict) -> str:
    if axes.get("volume") == "high":
        return "DELEGATE"
    return "DIRECT"


if __name__ == "__main__":
    print(naive_gate({"volume": "high", "spec_readiness": "vague"}))
    print(naive_gate({"volume": "high", "failcost": "high"}))

실행하면 둘 다 DELEGATE가 나온다.

그걸로 부족했던 지점

첫 번째 호출은 명세가 아직 vague(모호함)인데도 물량만 보고 위임을 확정한다. 명세가 확정되지 않은 상태로 위임하면 위임받은 쪽이 불확실한 목표를 놓고 탐색하다가 엉뚱한 결과를 들고 온다. 이건 이 판정에서 저지를 수 있는 가장 비싼 실수다 — 불분명한 목표를 놓고 비싼 실행 한 번을 통째로 날리기 때문이다. 명세부터 정리하라는 뜻의 PLAN_FIRST는 물량 체크보다 먼저 따져야 한다.

두 번째 호출은 더 까다롭다. failcost=high(실패 시 대가가 큼), 즉 대량 권한 변경이나 저장소 전체 리네이밍 같은 작업이다. 겉보기엔 기계적이지만 잘못되면 파급이 크다. 물량만 보는 판정기는 이런 것도 그냥 DELEGATE로 밀어버린다. 실제로는 "얕고(depth=shallow) 검증 가능하다(verifiable=yes)"는 조건 둘만으로는 기계적 배치로 단정하면 안 된다. 대량 권한 변경, 마이그레이션, 저장소 전체 리네이밍은 전부 얕고 검증 가능하지만 동시에 실패 비용이 높다. 두 조건만 보고 "기계적이니 위임해도 안전하다"고 판단하면 바로 이런 위험한 사례를 놓친다.

그리고 설령 안전하게 기계적 배치로 분류했다 해도 앞 절에서 다룬 문제가 남는다 — 위임이 실제로 더 싼지는 최적화 목표 없이는 답할 수 없다. 최소 해법에는 그렇게 되묻는 절차가 아예 없다.

최종형

이 세 구멍(명세 미확정, 위험한 배치를 기계적으로 오판, 최적화 목표 부재)을 메운 버전이다. 표준 라이브러리만 쓴다. 어디에 둬도 상관없으며 여기서는 route_advisor.py로 부른다.

#!/usr/bin/env python3
"""직접/위임 판정기 — 표준 라이브러리만 쓴다. 아무 폴더에나 둬도 된다."""
from __future__ import annotations
import argparse

OPT_GOALS = ("cost", "latency", "context_preservation")


def parse_kv(s: str) -> dict:
    out = {}
    for pair in s.split(","):
        pair = pair.strip()
        if not pair:
            continue
        k, _, v = pair.partition("=")
        out[k.strip()] = v.strip()
    return out


def is_mechanical_batch(axes: dict, ext: dict) -> bool:
    """shallow + verifiable 단둘로는 부족하다 — 전 조건을 다 걸어야 한다."""
    return (
        axes.get("depth") == "shallow"
        and axes.get("verifiable") == "yes"
        and axes.get("volume") == "high"
        and axes.get("failcost") != "high"
        and ext.get("spec_readiness") == "executable"
        and ext.get("decomposability") == "independent"
        and ext.get("context_dependency") == "low"
    )


def gate(axes: dict, ext: dict) -> dict:
    choices = {"verifiable": {"yes", "partial", "no"}, "failcost": {"low", "mid", "high"},
               "volume": {"low", "high"}, "depth": {"shallow", "mid", "deep"}}
    extra = {"handoff_cost": {"low", "high"}, "spec_readiness": {"executable", "vague"},
             "decomposability": {"independent", "single"}, "context_dependency": {"low", "high"},
             "verifier_available": {"yes", "no"}, "optimization_goal": set(OPT_GOALS)}
    if (set(axes) != set(choices) or set(ext) - set(extra)
            or any(not isinstance(v, str) or v not in choices[k] for k, v in axes.items())
            or any(not isinstance(v, str) or v not in extra[k] for k, v in ext.items())):
        return {"route": "PLAN_FIRST", "reason": "필수 축 누락·알 수 없는 값이 있다. 입력부터 확인한다."}
    if ext.get("spec_readiness") != "executable":
        return {
            "route": "PLAN_FIRST",
            "reason": "명세가 실행 가능한 상태(범위·완료조건·검증자)가 아니다. 먼저 정한다.",
        }

    if axes.get("volume") == "low" and (
        ext.get("handoff_cost") == "high" or ext.get("context_dependency") == "high"
    ):
        return {
            "route": "DIRECT",
            "reason": "위임 고정비(새 컨텍스트 구축 + 명세 작성)가 산출물 규모보다 크다.",
        }

    if ext.get("verifier_available") != "yes":
        return {"route": "PLAN_FIRST", "reason": "독립 검증자를 정한 뒤 위임을 판단한다."}

    if is_mechanical_batch(axes, ext):
        goal = ext.get("optimization_goal")
        if goal not in OPT_GOALS:
            return {
                "route": "NEEDS_PREFERENCE",
                "reason": (
                    "기계적 배치이지만 위임 워커에 경제형 로드아웃이 없다. "
                    "비용/시간/컨텍스트 보존 중 무엇이 우선인지 답해야 판정이 성립한다."
                ),
                "ask": "비용 / 완료시간 / 메인 컨텍스트 보존 중 무엇이 우선입니까?",
            }
        if goal == "cost":
            return {
                "route": "DIRECT",
                "reason": "비용 우선 — 직접 실행을 측정 후보로 삼는다. 모델 전환은 별도 판단이다.",
            }
        return {
            "route": "DELEGATE",
            "reason": f"{goal} 우선 — 위임은 병렬성·컨텍스트 보존을 산다(비용 절감이 아니다).",
        }

    if (
        ext.get("spec_readiness") == "executable"
        and (axes.get("volume") == "high" or ext.get("decomposability") == "independent")
        and ext.get("verifier_available") == "yes"
    ):
        return {
            "route": "DELEGATE",
            "reason": "명세 확정 + (물량 또는 분해 가능) + 독립 검증자 존재.",
        }

    return {
        "route": "DIRECT",
        "reason": "위 조건 중 어느 것도 확정적으로 위임을 지지하지 않는다.",
        "confidence": "low",
    }


def main():
    ap = argparse.ArgumentParser()
    ap.add_argument(
        "--axes", required=True,
        help="verifiable=yes|partial|no,failcost=low|mid|high,volume=high|low,depth=shallow|mid|deep",
    )
    ap.add_argument(
        "--axes-ext", default="",
        help=(
            "handoff_cost=low|high,spec_readiness=executable|vague,"
            "decomposability=independent|single,context_dependency=low|high,"
            "verifier_available=yes|no,optimization_goal=cost|latency|context_preservation"
        ),
    )
    args = ap.parse_args()
    axes = parse_kv(args.axes)
    ext = parse_kv(args.axes_ext)
    result = gate(axes, ext)
    print(f"route: {result['route']}")
    print(f"reason: {result['reason']}")
    if "ask" in result:
        print(f"ask: {result['ask']}")


if __name__ == "__main__":
    main()

마지막 두 예시를 나란히 보면 요지가 드러난다. failcost(실패 비용) 하나만 low에서 high로 바뀌었을 뿐인데 판정이 "되물어라"에서 "위임해도 된다"로 바뀐다. 실패 비용이 높은 작업은 애초에 "기계적 배치라서 값싸게 위임할지 말지 고민하는" 범주에 들지 못한다. 이런 작업은 명세·물량·검증자 조건을 정공법으로 통과해야만 위임될 수 있다.

판정 축이 미는 방향

축 위임(DELEGATE) 쪽으로 미는 값 직접(DIRECT) 쪽으로 미는 값
검증가능성(verifiable) yes — 결과를 기계적으로 확인 가능 no — 판단이 주관적이라 위임 결과를 믿고 넘어가기 어려움
실패비용(failcost) low/mid — 틀려도 되돌리기 쉬움 high — 틀리면 파급이 커서 직접 통제하고 싶어짐
물량(volume) high — 고정비를 상쇄할 만큼 큼 low — 고정비가 산출물보다 큼
깊이(depth) shallow — 반복적·기계적 deep — 세션의 누적 맥락이 필요
인계비용(handoff_cost) low — 브리프 작성이 짧게 끝남 high — 명세 작성 자체가 큰 일
명세성숙도(spec_readiness) executable — 넘길 게 확정돼 있음 vague — 넘기기 전에 정해야 함(→ PLAN_FIRST)
분해가능성(decomposability) independent — 쪼개서 병렬로 맡길 수 있음 single — 쪼개지지 않아 위임 이점이 없음
컨텍스트의존도(context_dependency) low — 현재 대화의 암묵 지식이 필요 없음 high — 위임받는 쪽이 그 맥락을 모름

이 예제의 판정 결과 네 가지

결과 뜻
DIRECT 지금 세션에서 직접 한다. 남은 선택은 모델·effort 두 축뿐이다.
PLAN_FIRST 명세(범위·완료조건·검증자)가 아직 실행 가능한 상태가 아니다. 위임이든 직접이든 먼저 명세를 정한다.
DELEGATE 다른 워커에게 맡긴다. 남은 선택은 어느 워커냐 하나뿐 — 그 워커의 모델·effort는 이미 고정돼 있다.
NEEDS_PREFERENCE 조건은 다 갖췄지만 최적화 목표(비용/시간/컨텍스트 보존)가 없어 답을 하나로 좁힐 수 없다. 답을 지어내지 않고 되묻는다.

직접 확인하는 법

먼저 위 예시들을 그대로 돌려 네 결과가 실제로 나오는지 확인한다. 그다음, 안전장치를 다루는 장답게 일부러 깨뜨려서 빨간불이 되는지 본다.

route_advisor.py를 임시 폴더에 route_advisor_broken.py로 복사한다. 아래 함수 이름에서 _broken을 빼고 기존 is_mechanical_batch를 교체한다. is_mechanical_batch의 전체 조건 중 depth와 verifiable 딱 두 개만 남기고 나머지를 지워보자.

def is_mechanical_batch_broken(axes: dict, ext: dict) -> bool:
    return (
        axes.get("depth") == "shallow"
        and axes.get("verifiable") == "yes"
    )

그리고 저장소 전체 권한 변경처럼 실패 비용이 높은 사례를 넣는다.

$ python3 route_advisor_broken.py --axes "verifiable=yes,failcost=high,volume=high,depth=shallow" \
    --axes-ext "spec_readiness=executable,decomposability=independent,context_dependency=low,verifier_available=yes"
route: NEEDS_PREFERENCE
reason: 기계적 배치이지만 위임 워커에 경제형 로드아웃이 없다. 비용/시간/컨텍스트 보존 중 무엇이 우선인지 답해야 판정이 성립한다.
ask: 비용 / 완료시간 / 메인 컨텍스트 보존 중 무엇이 우선입니까?

분류가 달라졌다. 정상판에서 DELEGATE가 나오는 이유는 실패 비용이 높아서가 아니라 별도의 명세·물량·검증자 조건을 통과했기 때문이다. 이 예제는 위험한 작업의 실행 승인이나 안전성을 판정하지 않는다. 그런데 두 조건만 보는 깨진 버전에 넣으면 이 사례가 "기계적 배치라서 비용/시간/컨텍스트 중 뭐가 중한지만 고르면 되는" 사소한 문제로 둔갑한다. 실패 비용이 높다는 신호가 판정 과정에서 사라져 버렸다. 그래서 얕고 검증 가능하다는 조건 둘만으로 "기계적"이라 부르면 안 된다 — 위험한 작업을 편안한 작업으로 오분류하면 정작 신중해야 할 순간에 "그냥 어느 쪽이 편하냐"만 묻게 된다.

체크리스트 — 인쇄해서 옆에 붙여둘 것

  1. 지금 조작 가능한 축이 뭔가? 위임을 본다면 "어느 워커냐" 하나뿐이다. 직접을 본다면 모델과 effort 두 개다. 없는 다이얼을 찾지 않는다.
  2. 명세가 실행 가능한가? 범위·완료조건·검증 방법이 안 정해졌다면 여기서 멈춘다 — PLAN_FIRST. 불분명한 목표로 비싼 실행을 낭비하면 그게 가장 비싼 실수다.
  3. 물량이 작고 인계비용·컨텍스트의존도가 크다면 → DIRECT. 위임 고정비(새 컨텍스트 구축 + 명세 작성)가 산출물보다 크다.
  4. 얕고, 검증 가능하고, 물량이 크고, 실패비용이 낮고, 명세가 확정됐고, 독립적으로 쪼개지고, 컨텍스트의존도가 낮다 — 일곱 조건 전부 맞다면 "기계적 배치"다. 이때는 위임이 당연한 답은 아니다. 최적화 목표(비용/시간/컨텍스트 보존)를 먼저 정한다. 없으면 → NEEDS_PREFERENCE.
  5. 명세 확정 + (물량 크거나 독립적으로 쪼개짐) + 독립 검증자 존재 → DELEGATE. 워커가 배차 설정에 고정된 모델·effort로 뛴다고 전제한다.
  6. 직접 실행의 모델·effort를 정하려면 벤더 환경부터 확인한다. 이 예제는 모델 선택을 구현하지 않으며 NEEDS_SURFACE도 반환하지 않는다.
  7. 위임이 곧 저렴하다고 말하지 않는다. 워커 가격뿐 아니라 캐시·토큰·검수 시간까지 함께 잰다. 직접-위임 실측 쌍이 없으면 비용 비교는 "측정되지 않음"이라고 정직하게 말한다.
