5장 — 실패했을 때 무엇을 올릴 것인가

기술 검증판 2026-09-28 · 원고 최종 수정 2026-09-28

증상
실패하면 반사적으로 effort 를 올린다. 또 실패한다. 원인은 딴 데 있었다
원인
실패에는 종류가 있는데 대응은 "더 세게 시킨다" 한 가지뿐이었다
붙일 장치
실패를 7가지로 나누고 종류마다 다른 손잡이를 당기는 진단표
그래도 부족했던 것
명세 부실인데도 모델 티어를 올리는 경로가 남아 있었다. 그걸 막는 것이 최종형이다

서브에이전트에게 리팩터링을 맡겼는데 테스트가 깨진 채로 돌아왔다. 반사적으로 effort를 한 단계 올려서 다시 시켰다. 또 깨졌다. 이번엔 모델 티어를 한 단계 올렸다. 또 깨졌다. 세 번째 시도에서야 로그를 제대로 읽었다 — 테스트 자체가 존재하지 않는 헬퍼 함수를 기대하고 있었다. 모델이 약해서가 아니었다. 내가 넘긴 명세와 완료조건이 애초에 앞뒤가 안 맞았다. 원인과 무관한 재시도를 두 번 더 해 비용이 늘었다. 원인과 무관한 effort와 티어를 차례로 올리고 나서야 진짜 문제를 봤다.

더 찜찜한 경험도 있다. 어느 워커에게 위험한 배치 작업을 맡겼는데 한 번에 성공했다. "이 워커·이 경로가 좋구나" 하고 다음에도 같은 조합을 썼다. 근거를 따져보니 성공은 딱 한 번이었다. 그 한 번이 경로가 안정적이라는 증거였을까, 아니면 운이었을까. 스스로도 답을 못 했다.

두 사고는 뿌리가 같다. 실패에는 종류가 있는데, 대응은 한 가지("더 세게 시킨다")뿐이었다. 성공에도 등급이 있는데 한 번 성공한 것을 검증된 근거처럼 취급했다.

왜 그런가

1추론깊이 부족
effort 한 단계 ↑ — effort 증량을 시험할 칸
2모델 역량 부족
effort 말고 티어를 올린다
3명세 부실
연산량을 올리지 않는다. 명세와 완료조건을 고친다
4구현 버그
같은 조건으로 한 번만 국소 수선
5도구·인프라 문제
아무것도 바꾸지 않는다. 환경을 고친다
6과잉 투입
한 단계 낮추고 멈출 조건을 명시
7역할·벤더 불일치
다른 워커를 제안한다
그래서
이 진단표는 1번에서 effort 증량을 먼저 시험한다. 원인이 겹칠 수 있으므로 재시도 결과를 보고 진단을 고친다
초록은 effort 증량을 먼저 시험할 칸, 빨강은 다른 대응을 먼저 검토할 칸이다. 실패했을 때 손이 먼저 가는 손잡이는 대개 1번용이다.

"effort를 올린다"와 "모델을 바꾼다"는 서로 다른 대응이다. 전자는 같은 모델의 추론 자원 설정을 바꾸고 후자는 모델 자체를 바꾼다. 둘 다 비용을 늘릴 수 있지만 효과를 보장하지는 않는다. 명세·도구·환경이 실패 원인이라면 그 원인부터 고쳐야 한다.

가장 흔하고 가장 비싼 오진은 명세 부실을 모델 역량 부족으로 착각하는 것이다. 테스트를 문자 그대로는 통과시켰지만 요구사항의 취지는 놓친 경우, 완료조건이 애매해서 워커가 나름대로 해석해 만든 경우 — 이런 결과물은 겉보기엔 "틀렸다"로 보이지만 원인은 워커의 지능이 아니라 내가 건넨 명세에 있다. 이걸 모델 부족으로 오진하면 티어를 올리는 데 비용을 쓰고, 다음 시도도 똑같이 애매한 명세를 받아 똑같이 애매한 결과를 낸다.

두 번째 문제는 증거의 무게다. 한 번 성공했다고 그 경로가 좋다고 볼 수는 없다. 표본이 하나뿐이면 그 성공은 우연일 수도, 필연일 수도 있고 구분할 방법이 없다. 그런데도 "한 번 됐으니 다음에도 이렇게 하자"고 판단하기가 아주 쉽다. 이걸 막으려면 "몇 번을 봐야 믿을 만한가"에 대한 정직한 기준이 필요하다.

최소 해법

가장 단순한 대응은 이렇다. 실패하면 무조건 effort를 한 단계 올리고, 그래도 안 되면 모델을 올린다.

#!/usr/bin/env python3
"""최소 해법 — 실패하면 무조건 연산량을 늘린다. 구멍이 있다."""

LADDER = ("low", "medium", "high")


def naive_escalate(effort: str) -> str:
    i = LADDER.index(effort)
    return LADDER[i + 1] if i + 1 < len(LADDER) else "raise_model_tier"


if __name__ == "__main__":
    print(naive_escalate("low"))     # -> medium
    print(naive_escalate("medium"))  # -> high
    print(naive_escalate("high"))    # -> raise_model_tier

이 함수는 실패의 원인을 전혀 묻지 않는다. 그냥 다음 단계로 넘어간다.

그걸로 부족했던 지점

앞서 든 리팩터링 사례를 이 함수에 넣어보면 바로 드러난다. 실패 원인은 "테스트가 존재하지 않는 헬퍼를 기대함" — 명세 부실이다. naive_escalate는 이 경우에도 medium → high → raise_model_tier 순서로 그저 연산량과 티어를 올리라고 답한다. 이 함수 자체는 모델이나 테스트를 실행하지 않는다. 위 사례에서는 원인을 고치지 않은 재시도가 실패했다. effort나 티어만 올린다고 잘못된 명세가 해결된다고 볼 수는 없다. 이 함수에는 "테스트를 문자 그대로만 통과시켰다"거나 "인증 오류"라는 신호를 받아줄 자리가 아예 없다.

도구·인프라 문제는 더 위험하다. 인증 만료나 네트워크 장애로 실패했는데 이걸 "모델이 못 했다"로 기록하면, 그 기록이 나중에 "이 모델·이 경로는 별로다"라는 잘못된 학습 데이터가 된다. 환경 문제를 모델 품질 문제로 뒤집어씌우면 그 뒤로 내리는 판정이 전부 오염된다.

앞서 짚은 증거의 문제 — 성공 한 번을 믿을 만한 근거로 취급하는 문제는, 애초에 이 함수의 관심사 밖이다. "언제 재시도할까"만 다루고 "언제 믿을까"는 다루지 않는다.

실패 7분류표

분류마다 먼저 시험할 대응이 다르다. 원인이 겹칠 수 있으므로 한 번의 분류를 확정 진단으로 취급하지 않는다.

증상 분류 식별 방법 정확한 대응
effort가 낮을 때 얕거나 틀림. 명세도 도구도 문제없음 추론깊이 부족 같은 명세·같은 도구로 effort만 올려서 재시도했을 때 나아지는지 본다 같은 모델에서 effort 한 단계만 올린다
명세·도구·환경 문제를 배제해도 반복 실패 모델 역량 부족 후보 완료조건과 실패 양상을 검토하고 같은 과제에서 다른 모델과 비교 모델 변경을 시험한다. 최고 effort에서 실패했다는 사실만으로 확정하지 않는다
테스트는 통과했는데 요구사항의 정신을 놓침. 검사를 문자 그대로만 만족 명세 부실 통과 기준을 다시 읽어보면 애매하거나 반례를 안 막아뒀다 연산량을 올리지 않는다. 명세와 완료조건을 고친다
경계가 뚜렷한 버그 하나 구현 버그 원인 함수·라인을 특정할 수 있다 같은 모델·같은 effort로 한 번만 국소 수선
인증 만료, 쿼터 초과, 네트워크 오류, 권한 거부 도구·인프라 문제 에러 메시지가 모델 출력이 아니라 시스템·CLI 오류다 아무것도 바꾸지 않는다. 환경을 고친다. 절대 모델 품질 실패로 기록하지 않는다
품질은 충분한데 느리고 비쌈. 끝없이 다듬기만 함 과잉 투입 결과물이 이미 완료조건을 만족하는데 계속 도는 중 한 단계 낮추고 멈출 조건을 명시한다
특화가 안 맞음. 이 워커·이 벤더의 강점 밖 작업 역할·벤더 불일치 같은 종류 작업에서 다른 워커는 잘하는데 이 워커만 반복 실패 다른 워커를 제안한다. 벤더는 자동으로 바꾸지 않는다

가장 자주 틀리는 지점을 한 번 더 강조한다. 명세 부실을 모델 역량 부족으로 오진하는 것. 판별법은 간단하다 — 통과 기준(완료조건, 테스트, DoD)을 다시 소리 내어 읽어봤을 때 애매한 구석이 있는가? 있다면 명세부터 고친다. 모호함을 제거해도 실패한다면 도구·환경·구현 버그를 점검한 뒤 모델 역량을 원인 후보로 검토한다. 순서를 지키지 않으면 티어를 계속 올리면서 같은 애매한 명세를 반복해서 먹이게 된다.

이 장의 코드는 low → medium → high라는 예제용 세 단계만 쓴다. 제품·모델마다 지원 값이 다르므로 보편적인 최고 단계라고 읽으면 안 된다. 상한에 닿으면 명세·도구·역량 진단으로 돌아간다. 한 번에 축 하나만 바꾸는 것은 원인 비교를 위한 실험 규칙이지, 모델을 바꾸면 반드시 해결된다는 법칙이 아니다.

1/1 성공은 증거가 아니다

같은 성공 확률을 가진 독립 시행이라는 이항모형을 가정하고 표본의 불확실성을 보자. 여기서는 Wilson 양측 95% 신뢰구간의 하한을 쓴다. "참 성공률이 이 값 이상일 확률이 95%"라는 뜻도, 최악의 경우 보장도 아니다. 같은 절차로 표본을 반복 수집할 때 구간이 참값을 포함하는 빈도를 기준으로 만든 근사 구간이다. 표본 수가 작으면 근사 오차도 주의해야 한다.

전부 성공한 작은 표본은 운 좋게 얻은 결과일 수 있다. 서로 다른 모델·과제·설정을 한데 섞거나 실패한 시도를 빼고 계산하면 이 구간을 전체 성공률의 근거로 쓸 수 없다.

계산식은 다음과 같다(z=1.96, 95% 신뢰수준).

import math


def wilson_lower_bound(successes: int, n: int, z: float = 1.96) -> float:
    if type(n) is not int or type(successes) is not int or not 0 <= successes <= n:
        raise ValueError("0 <= successes <= n인 정수 개수가 필요하다")
    if isinstance(z, bool) or not isinstance(z, (int, float)) or not math.isfinite(z) or z <= 0:
        raise ValueError("z는 유한한 양수여야 한다")
    if n == 0:
        return 0.0  # 증거 없음 표시; 계산된 신뢰구간이 아니다
    phat = successes / n
    denom = 1 + z**2 / n
    center = phat + z**2 / (2 * n)
    margin = z * math.sqrt((phat * (1 - phat) + z**2 / (4 * n)) / n)
    return (center - margin) / denom


for x, n in ((1, 1), (3, 3), (10, 10), (20, 20)):
    print(f"{x}/{n} 전부 성공 -> 하한 {wilson_lower_bound(x, n) * 100:.1f}%")

실제로 돌려서 검산한 값이다.

1/1 전부 성공 -> 하한 20.7%
3/3 전부 성공 -> 하한 43.8%
10/10 전부 성공 -> 하한 72.2%
20/20 전부 성공 -> 하한 83.9%

한 번 성공했을 때 하한은 약 20.7%다. 구간이 넓다는 사실은 한 번의 성공으로 높은 신뢰성을 주장하기 어렵다는 것을 보여준다. 다음 작업이 최소 20% 확률로 성공한다고 보장하는 값은 아니다.

아래 3·10·20건 기준은 이 책의 보수적인 운영 정책이다. 통계학이 정한 합격선이나 보편적인 안전 기준이 아니다.

그래서 표본 크기에 따라 증거를 얼마나 믿을지 이렇게 나눈다.

유사 사례 수 취급
0~2건 일화(anecdotal) — 참고만 하고 기존 판단을 뒤집지 않는다
3~9건 잠정(provisional) — 동점 상황의 타이브레이커 정도로만 쓴다
10건 이상 기존 판단을 뒤집을 후보가 된다
20건 이상 (실패비용이 높은 작업) 뒤집을 후보가 되려면 이 정도는 필요하다

그리고 표본이 몇 건이든, 다음 세 조건을 만족하지 못하면 애초에 후보에도 못 오른다. 서로 다른 작업 사례가 3건 미만이면(같은 작업을 여러 번 반복한 건지 진짜 다양한 사례인지 확인), 실패나 부분 성공이 하나라도 섞여 있으면, 또는 검증자가 산출자 본인이면 — 이 셋 중 하나라도 걸리면 이 정책에서 기존 기본값을 뒤집는 후보로 채택하지 않는다. 실패·부분 성공도 유효한 관측이므로 성공률 계산과 원인 분석에서는 빼면 안 된다.

검증 등급 — 누가 채점했는가

성공 여부를 누가 판정했는지에 따라서도 표본을 얼마나 믿을지가 달라진다.

등급 뜻
V3 결정론적 테스트, 스키마 검증, 정확한 출력 비교, 렌더링 확인
V2 사람 또는 독립 리뷰어가 사전에 정한 완료조건에 대고 판단
V1 실행자가 아닌 감독 쪽의 구조화된 검토
V0 워커의 자기보고, 또는 근거 없는 "됐습니다"

산출자가 자기 결과를 채점하면 안 된다는 원칙이 여기서도 반복된다. 이 책 앞부분에서 "종료코드 0은 증거가 아니다"라고 짚은 것과 같은 구멍이다. 워커가 "테스트 통과했습니다"라고 자기 입으로 말한 것(V0)과, 실행 근거와 사전에 정한 테스트를 독립적으로 확인한 것(V3)은 믿을 수 있는 정도가 완전히 다르다. 프로세스나 검증자 이름이 다르다는 사실만으로 독립성이 생기지는 않는다. 작업자가 만든 허술한 테스트를 별도 프로세스가 돌리는 경우도 있기 때문이다. 아래 코드는 식별자와 등급 필드의 기본 제약만 확인하며, 검증자의 실체·권한·테스트 품질은 별도로 확인해야 한다.

V0만 있는 기록은 저장은 해두되, 판정에는 절대 반영하지 않는다. V2·V3라 해도 검증자가 산출자 본인이면 즉시 무효로 처리한다 — 등급이 높아도 "누가 채점했는가"를 속이면 소용없다.

결과를 기록하는 법 — append-only, 정정은 무효화 이벤트로

증거를 쌓으려면 시도할 때마다 결과를 기록해야 한다. 성공만 기록하면 모든 경로가 좋아 보이는 착시에 빠진다. 종료된 시도는 성공·실패·중도 포기·추천을 무시한 강행까지 전부 기록한다. 승리만 기록하는 습관은 학습 루프 전체를 오염시킨다.

기록 방식에서 지켜야 할 규칙이 하나 있다. 기존 줄을 절대 덮어쓰지 않는다. 나쁜 기록을 발견했다고 그 줄을 지우거나 고치면 그 기록을 근거로 과거에 왜 그렇게 판정했는지 추적할 방법이 사라진다. 나중에 "이 경로가 왜 안전하다고 판단됐었지?"를 되짚을 때, 덮어쓴 파일에는 답이 없다. 대신 무효화 이벤트를 추가로 append한다. 원본 기록은 그대로 남기고, "이 시도는 이런 이유로 무효"라는 새 줄을 뒤에 붙인다. 그러면 파일을 처음부터 끝까지 읽었을 때 무엇이 있었고 무엇이 왜 취소됐는지 전부 감사할 수 있다. 덮어쓰기는 과거를 지운다. append는 과거를 남겨 둔 채 그 위에 정정을 쌓는다.

최종형

7분류 진단, Wilson 하한, append-only 레지스트리(기록·무효화·유효표본 필터링)를 하나로 묶은 코드다. 표준 라이브러리만 쓴다. 어디에 둬도 되며, 여기서는 failure_diagnosis.py로 부른다.

#!/usr/bin/env python3
"""실패 분류 + Wilson 하한 + append-only 레지스트리. 표준 라이브러리만 쓴다."""
from __future__ import annotations
import json
import math
import sys
from pathlib import Path

NORMAL_EFFORT_LADDER = ("low", "medium", "high")


def wilson_lower_bound(successes: int, n: int, z: float = 1.96) -> float:
    """일반 성공/시도 개수의 Wilson 양측 95% 신뢰구간 하한."""
    if type(n) is not int or type(successes) is not int or not 0 <= successes <= n:
        raise ValueError("0 <= successes <= n인 정수 개수가 필요하다")
    if isinstance(z, bool) or not isinstance(z, (int, float)) or not math.isfinite(z) or z <= 0:
        raise ValueError("z는 유한한 양수여야 한다")
    if n == 0:
        return 0.0  # 증거 없음 표시; 계산된 신뢰구간이 아니다
    phat = successes / n
    denom = 1 + z**2 / n
    center = phat + z**2 / (2 * n)
    margin = z * math.sqrt((phat * (1 - phat) + z**2 / (4 * n)) / n)
    return (center - margin) / denom


def evidence_tier(n: int) -> str:
    if n <= 2:
        return "anecdotal"
    if n <= 9:
        return "provisional"
    return "override_eligible"


def next_effort(effort: str) -> str | None:
    if effort not in NORMAL_EFFORT_LADDER:
        return None
    i = NORMAL_EFFORT_LADDER.index(effort)
    return NORMAL_EFFORT_LADDER[i + 1] if i + 1 < len(NORMAL_EFFORT_LADDER) else None


def diagnose(failure_class: str, model: str | None = None, effort: str | None = None) -> dict:
    """리트라이마다 축을 딱 하나만 바꾼다."""
    if failure_class in {"REASONING_DEPTH_FAILURE", "OVERPROVISIONING"} and effort not in NORMAL_EFFORT_LADDER:
        return {"change_axis": "none", "rationale": "지원되는 effort 값을 먼저 확인한다."}
    if failure_class == "REASONING_DEPTH_FAILURE":
        if next_effort(effort) is None:
            return {"change_axis": "none", "rationale": "effort 상한이다. 명세·도구·역량 진단을 다시 한다."}
        return {"change_axis": "effort", "from": effort, "to": next_effort(effort),
                "rationale": "숙고가 부족했다. 같은 모델에서 effort를 한 단계만 올린다."}
    if failure_class == "MODEL_CAPABILITY_FAILURE":
        return {"change_axis": "model", "from": model,
                "rationale": "명세·도구 문제를 배제하고 역량 부족으로 진단했다면 모델 변경을 시험한다."}
    if failure_class == "SPEC_FAILURE":
        return {"change_axis": "spec",
                "rationale": "테스트를 문자 그대로만 통과시켰다. 연산량이 아니라 명세·완료조건을 고친다."}
    if failure_class == "IMPLEMENTATION_BUG":
        return {"change_axis": "none",
                "rationale": "경계가 뚜렷한 버그다. 같은 모델·같은 effort로 한 번만 수선한다."}
    if failure_class == "TOOL_OR_INFRA_FAILURE":
        return {"change_axis": "none",
                "rationale": "인증·쿼터·네트워크·권한 문제다. 아무것도 바꾸지 않는다 — 환경을 고친다. "
                             "절대 모델 품질 실패로 기록하지 않는다."}
    if failure_class == "OVERPROVISIONING":
        if effort == NORMAL_EFFORT_LADDER[0]:
            return {"change_axis": "none", "rationale": "이 예제의 effort 하한이다. 다른 비용 원인을 확인한다."}
        return {"change_axis": "effort",
                "from": effort,
                "to": NORMAL_EFFORT_LADDER[max(0, NORMAL_EFFORT_LADDER.index(effort) - 1)],
                "rationale": "품질은 충분한데 느리고 비싸다. 한 단계 낮추고 멈출 조건을 명시한다."}
    if failure_class == "ROLE_OR_VENDOR_MISMATCH":
        return {"change_axis": "worker",
                "rationale": "특화가 안 맞는다. 다른 워커를 제안한다 — 벤더는 자동으로 바꾸지 않는다."}
    return {"change_axis": "none", "rationale": f"미분류 실패 종류: {failure_class}"}


# ---------- append-only 레지스트리 ----------

def record_attempt(path: Path, **fields) -> None:
    fields.setdefault("event_type", "attempt_final")
    with path.open("a", encoding="utf-8") as f:
        f.write(json.dumps(fields, ensure_ascii=False) + "\n")


def invalidate_attempt(path: Path, target_attempt_id: str, reason_code: str,
                        evidence: str, event_id: str) -> None:
    event = {
        "event_type": "attempt_invalidation",
        "event_id": event_id,
        "target_attempt_id": target_attempt_id,
        "reason_code": reason_code,
        "verification_evidence": evidence,
    }
    with path.open("a", encoding="utf-8") as f:
        f.write(json.dumps(event, ensure_ascii=False) + "\n")


def load_records(path: Path) -> list[dict]:
    if not path.exists():
        return []
    return [json.loads(line) for line in path.read_text(encoding="utf-8").splitlines() if line.strip()]


def usable_attempts(records: list[dict], cohort: dict | None = None) -> list[dict]:
    """V2/V3 + 독립 검증자 + 무효화되지 않은 것만, attempt_id로 중복 제거."""
    if any(not isinstance(r, dict) for r in records):
        raise ValueError("레지스트리의 각 줄은 JSON 객체여야 한다")
    invalidated = set()
    for r in records:
        if r.get("event_type") == "attempt_invalidation":
            target = r.get("target_attempt_id")
            if not isinstance(target, str) or not target.strip():
                raise ValueError("무효화 이벤트의 대상 식별자가 비었다")
            invalidated.add(target)
    by_id: dict[str, list[dict]] = {}
    for r in records:
        aid = r.get("attempt_id")
        if r.get("event_type", "attempt_final") == "attempt_final" and isinstance(aid, str) and aid.strip():
            by_id.setdefault(aid, []).append(r)
    conflicts = {aid for aid, rows in by_id.items() if any(row != rows[0] for row in rows)}
    seen: set[str] = set()
    out: list[dict] = []
    for r in records:
        if r.get("event_type", "attempt_final") != "attempt_final":
            continue
        if r.get("verification_grade") not in ("V2", "V3"):
            continue
        verifier = str(r.get("verifier_role") or "").strip().lower()
        worker = str(r.get("worker") or "").strip().lower()
        if not verifier or verifier in {"self", "producer", "worker"} or verifier == worker:
            continue
        aid = r.get("attempt_id")
        if any(not isinstance(r.get(k), str) or not r[k].strip() for k in ("attempt_id", "task", "worker", "verifier_role")):
            continue
        if r.get("outcome") not in ("success", "fail", "partial", "aborted") or aid in conflicts:
            continue
        if aid in invalidated or aid in seen:
            continue
        if cohort and any(r.get(k) != v for k, v in cohort.items()):
            continue
        seen.add(aid)
        out.append(r)
    return out


def override_allowed(usable: list[dict], failcost: str = "low") -> dict:
    if failcost not in {"low", "mid", "high"}:
        raise ValueError("알 수 없는 failcost")
    usable = usable_attempts(usable)
    n = len(usable)
    unique_tasks = len({r.get("task") for r in usable})
    success = sum(1 for r in usable if r.get("outcome") == "success")
    fail = sum(1 for r in usable if r.get("outcome") == "fail")
    partial = sum(1 for r in usable if r.get("outcome") == "partial")
    all_success = n > 0 and success == n and fail == 0 and partial == 0
    need = 20 if failcost == "high" else 10
    allowed = n >= need and unique_tasks >= 3 and all_success
    return {
        "allowed": allowed, "n": n, "tier": evidence_tier(n),
        "unique_task_instances": unique_tasks, "success": success, "fail": fail, "partial": partial,
        "wilson_lower_bound": round(wilson_lower_bound(success, n), 3) if n else 0.0,
    }


if __name__ == "__main__":
    reg = Path(sys.argv[1]) if len(sys.argv) > 1 else Path("registry_demo.jsonl")
    print("Wilson 95% 하한 —")
    for x, n in ((1, 1), (3, 3), (10, 10), (20, 20)):
        print(f"  {x}/{n} 전부 성공 -> {wilson_lower_bound(x, n) * 100:.1f}%  ({evidence_tier(n)})")

    record_attempt(reg, attempt_id="a1", task="배치 업로드 파서 수정", worker="worker-b",

직접 확인하는 법

1. Wilson 하한을 직접 검산한다. 위 코드를 그대로 돌려서 20.7% / 43.8% / 72.2% / 83.9%가 나오는지 확인한다. 표본을 30개, 50개로 늘려가며 하한이 어떻게 올라가는지도 관찰해본다 — 같은 조건에서 전부 성공한 표본이 늘면 계산된 하한이 올라간다. 실제 기록에 실패가 추가되면 하한이 내려갈 수도 있다.

2. 무효화가 실제로 걸러지는지 확인한다.

아래 실습은 앞서 저장한 failure_diagnosis.py와 같은 디렉터리의 새 파일에서 실행한다. 결과 파일이 없는 임시 폴더에서 시작한다.

from pathlib import Path
from failure_diagnosis import record_attempt, invalidate_attempt, usable_attempts, load_records

reg = Path("registry_audit.jsonl")
record_attempt(reg, attempt_id="b1", task="배치 이름변경", worker="worker-b",
               verification_grade="V3", verifier_role="pytest", outcome="success")
print("무효화 전:", len(usable_attempts(load_records(reg))))   # -> 1

invalidate_attempt(reg, target_attempt_id="b1", reason_code="verifier_was_producer",
                    evidence="검증자가 실행자 본인이었음이 뒤늦게 밝혀짐", event_id="inv-1")
print("무효화 후:", len(usable_attempts(load_records(reg))))   # -> 0
print("파일 줄 수(둘 다 남아 감사 가능):", sum(1 for _ in open(reg)))  # -> 2

3. 안전장치를 일부러 깨뜨린다. usable_attempts에서 "검증자가 산출자 본인이면 제외" 조건을 지워보자.

def usable_attempts_broken(records, cohort=None):
    invalidated = {r.get("target_attempt_id") for r in records if r.get("event_type") == "attempt_invalidation"}
    seen, out = set(), []
    for r in records:
        if r.get("event_type", "attempt_final") != "attempt_final":
            continue
        if r.get("verification_grade") not in ("V2", "V3"):
            continue
        aid = r.get("attempt_id")           # 검증자 == 산출자 체크가 사라졌다
        if aid in invalidated or aid in seen:
            continue
        seen.add(aid)
        out.append(r)
    return out

그리고 워커가 스스로를 "V3"로 자칭한 기록을 넣는다.

위 usable_attempts_broken 함수를 저장한 파일 아래에 다음 코드를 붙여 실행한다.

from pathlib import Path
from failure_diagnosis import record_attempt, usable_attempts, load_records

reg2 = Path("registry_selfcert.jsonl")
record_attempt(reg2, attempt_id="c1", task="배치 이름변경", worker="worker-b",
               verification_grade="V3", verifier_role="worker-b", outcome="success")

print("정상판(검증자==실행자면 제외):", len(usable_attempts(load_records(reg2))))          # -> 0
print("깨진판(검증자 체크 제거 -> 자기증명이 세어짐):", len(usable_attempts_broken(load_records(reg2))))  # -> 1

빨간불이다. 정상 버전은 산출자가 스스로를 "V3"라고 자칭한 기록을 표본에서 뺀다. 검증자 체크를 지운 깨진 버전은 그 자기증명을 그대로 세어버린다. 등급 표기(V3)만 믿고 "누가 채점했는가"를 확인하지 않으면 워커가 자기 자신을 검증자로 세우고 스스로에게 최고 등급을 매겨도 막을 방법이 없다.

실패 진단표 — 인쇄해서 옆에 붙여둘 것

증상 분류 정확한 대응
effort 낮을 때만 얕음/틀림 추론깊이 부족 같은 모델, effort +1단계
명세·환경 문제를 배제해도 반복 실패 모델 역량 부족 후보 모델 변경을 시험
통과는 했는데 요구의 정신을 놓침 명세 부실 연산량 그대로, 명세·완료조건 수정
원인 라인을 특정할 수 있는 버그 구현 버그 같은 모델·effort로 1회 국소 수선
인증/쿼터/네트워크/권한 오류 도구·인프라 문제 아무것도 바꾸지 않음, 환경만 고침
품질 충분한데 계속 다듬기만 함 과잉 투입 effort -1단계 + 멈출 조건 명시
이 워커·벤더 강점 밖 작업 역할·벤더 불일치 다른 워커 제안, 벤더 자동 전환 금지
  • 재시도할 때는 축을 딱 하나만 바꾼다.
  • 1~2건의 성공은 일화다. 3~9건은 잠정, 10건 이상(고위험 작업은 20건 이상)이라야 기존 판단을 뒤집을 후보가 된다 — 단, 서로 다른 사례 3건 이상 + 전부 성공 + 산출자와 검증자가 다를 때만.
  • 실패도, 중단도, 추천을 무시한 강행도 전부 기록한다. 승리만 기록하면 모든 경로가 좋아 보인다.
  • 정정은 덮어쓰기가 아니라 무효화 이벤트 추가로. 과거 판단이 왜 그렇게 내려졌는지 나중에 되짚을 수 있어야 한다.

계산식 근거: NIST 신뢰구간 설명, 확인 2026-09-28. JSONL 예제는 단일 작성자용이다. 동시 쓰기 잠금·서명·변조 방지는 구현하지 않았다. 같은 attempt_id의 상충 기록은 전부 제외하고 정정 사유를 조사한다.
