프롬프트만으로 통과한 리뷰

리뷰를 워커 하나에 맡겼다. 브리프에는 파일 세 개의 경로를 적어줬고 "이 파일들을 읽고 로직 오류를 찾으라"고 썼다. 5초 만에 답이 돌아왔다. "검토 완료. 세 파일 모두 로직 오류 없음. 다만 두 번째 파일의 예외 처리가 다소 느슨함." 문장은 매끄러웠고 지적도 그럴듯했다.

이 장이 false-PASS 라고 부르는 것 — 리뷰가 실패한 게 아니라, 리뷰를 하지 않고도 실패하지 않은 것처럼 보이는 응답이 나온 것이다. 파이프라인의 어느 검사도 세 번째 칸을 보지 않았다.

세 파일은 합쳐서 40KB가 넘었다. 사람이 제대로 읽으면 최소 몇 분은 걸릴 분량이었다. 시간만으로 읽기 여부를 판정할 수는 없었다. 나중에 로그를 뜯어보니 워커는 파일을 여는 도구를 호출한 적이 없었다. 브리프에 적힌 파일명과 프로젝트 맥락만 보고 "이런 종류의 코드는 대개 이런 지적을 받는다"는 패턴을 그럴듯하게 채워 넣었던 것이다. 이 장에서는 이것을 false-PASS라 부른다 — 리뷰가 실패한 게 아니라, 리뷰를 하지 않고도 실패하지 않은 것처럼 보이는 응답이 나온 것.

0장에서 세운 사다리로 보면 이 사고는 ⑤와 ⑥ 사이에서 났다. 프로세스는 실행됐고 응답도 받았다(⑤). 그런데 응답 내용이 정말 지시받은 입력에 근거했는지는 아무도 확인하지 않았다(⑥ 미달). 이 장은 이 틈을 메우는 장치들의 역사다 — 그리고 그 장치들이 하나씩 뚫렸던 기록이다.

최소 해법 — 라이브 저장소 대신 스냅샷

가장 먼저 워커가 볼 수 있는 것부터 줄였다. 워커에게 프로젝트 전체 저장소를 열어주면 워커가 정말 지시받은 파일을 읽었는지 아니면 근처의 다른 파일·다른 워커의 이전 결과·승인 로그를 곁눈질해서 답을 짜맞췄는지 구분할 방법이 없다. 그래서 호출마다 새 스냅샷을 만들고 워커의 작업 디렉터리(cwd)를 그곳으로 정했다. cwd 변경은 파일 배치일 뿐 접근 제한이 아니다. 상위 경로·절대경로·네트워크로 나가지 못하게 하려면 별도 샌드박스나 OS 권한이 필요하다.

이 스냅샷에는 딱 두 가지만 들어간다 — 워커 자신의 브리프 파일 하나, 그리고 sources/ 디렉터리. 다른 워커의 브리프, 이미 나온 다른 워커의 결과, 승인 상태, 작업 로그는 전부 스냅샷 밖에 남는다. 워커가 "다른 리뷰어는 이미 통과시켰던데" 같은 답을 내놓을 수 없도록 그런 정보는 스냅샷에 넣지 않는다. 스냅샷 밖의 정보를 읽지 못하는지는 별도 격리 설정으로 검증해야 한다.

이 파일은 tools/build_worker_snapshot.py에 둔다.

#!/usr/bin/env python3
"""워커 스냅샷을 만든다: brief.md + sources/ 만 담고, 검증용 1회성 문자열을 심는다."""
from __future__ import annotations

import secrets
import shutil
import sys
from pathlib import Path


def build_snapshot(snapshot_root: Path, brief_text: str, source_files: dict[str, str]) -> str:
    """snapshot_root 아래에 brief.md와 sources/를 만들고, 심어 넣은 nonce 값을 돌려준다.

    source_files: {"파일명": "내용"} — 워커에게 보여줄 원본만 여기 담는다.
    다른 워커의 결과·로그·승인 상태는 이 함수의 인자로도 받지 않는다.
    """
    reserved = "source-access-proof.txt"
    for name in source_files:
        rel = Path(name)
        if rel.is_absolute() or ".." in rel.parts or name in {"", ".", reserved}:
            raise ValueError(f"허용되지 않는 소스 경로: {name}")
    snapshot_root.mkdir(mode=0o700, parents=True, exist_ok=False)
    sources_dir = snapshot_root / "sources"
    sources_dir.mkdir(parents=True)
    snapshot_root.chmod(0o700)

    nonce = secrets.token_hex(16)
    (snapshot_root / "brief.md").write_text(brief_text, encoding="utf-8")
    for name, content in source_files.items():
        target = sources_dir / name
        target.parent.mkdir(parents=True, exist_ok=True)
        target.write_text(content, encoding="utf-8")
    (sources_dir / "source-access-proof.txt").write_text(nonce + "\n", encoding="utf-8")

    _assert_nonce_unique(snapshot_root, nonce)
    return nonce


def _assert_nonce_unique(snapshot_root: Path, nonce: str) -> None:
    hits = 0
    for path in snapshot_root.rglob("*"):
        if path.is_file():
            hits += path.read_text(encoding="utf-8", errors="replace").count(nonce)
    if hits != 1:
        raise RuntimeError(f"nonce가 스냅샷 전체에서 {hits}번 발견됨 — 정확히 1번이어야 한다")


if __name__ == "__main__":
    root = Path(sys.argv[1]) if len(sys.argv) > 1 else Path("./worker-snapshot")
    value = build_snapshot(
        root,
        brief_text=(
            "이 브리프에 실린 파일들만 근거로 리뷰하라. 응답 첫 줄에\n"
            "SOURCE_ACCESS_PROOF:<sources/source-access-proof.txt의 값>을 그대로 적어라."
        ),
        source_files={"target.py": "def add(a, b):\n    return a + b\n"},
    )
    print(f"snapshot 생성 완료: {root} (nonce는 출력하지 않음)")

스냅샷에는 다른 워커 결과가 없으므로 실수로 함께 전달할 가능성을 줄인다. 접근 차단까지 성립하려면 별도 격리가 필요하다. 위 생성기는 기존 디렉터리를 덮어쓰거나 삭제하지 않고 새 경로만 받는다. 그런데 이렇게만 해서는 "응답이 스냅샷에만 둔 값을 알고 있는지"를 여전히 증명할 수 없다. 브리프만 읽고도 그럴듯한 리뷰를 쓰는 문제는 그대로 남는다.

1회성 nonce — source-access-proof.txt

그래서 스냅샷 안에 그 파일을 열어야만 알 수 있는 값을 심었다. 호출마다 새로 생성한 임의 문자열을 sources/source-access-proof.txt에 단 한 줄로 넣고 워커에게는 응답의 정해진 위치에 SOURCE_ACCESS_PROOF:<값> 형태로 그 줄을 정확히 그대로 되뱉으라고 요구했다. 위 스크립트의 _assert_nonce_unique가 강제하듯 이 값은 스냅샷 전체에서 정확히 한 번만 나타나야 한다 — 브리프에도, 다른 소스 파일에도 없어야 한다.

이 파일은 tools/verify_source_access.py에 둔다.

#!/usr/bin/env python3
"""워커 응답이 스냅샷을 실제로 열었다는 증거(1회성 nonce)를 담고 있는지 검사한다."""
from __future__ import annotations

import sys
import re
from pathlib import Path


def expected_nonce(snapshot_root: Path) -> str:
    proof_file = snapshot_root / "sources" / "source-access-proof.txt"
    return proof_file.read_text(encoding="utf-8").strip()


def verify(response_text: str, snapshot_root: Path, required_line_index: int = 0) -> bool:
    if type(required_line_index) is not int or required_line_index < 0:
        return False
    try:
        nonce = expected_nonce(snapshot_root)
    except OSError:
        return False
    if not re.fullmatch(r"[0-9a-f]{32}", nonce):
        return False
    lines = [ln for ln in response_text.splitlines() if ln.strip() != ""]
    if len(lines) <= required_line_index:
        return False
    expected_line = f"SOURCE_ACCESS_PROOF:{nonce}"
    actual_line = lines[required_line_index].strip()
    # "포함"이 아니라 그 줄 전체가 정확히 일치해야 한다.
    return actual_line == expected_line


if __name__ == "__main__":
    root = Path(sys.argv[1])
    response = Path(sys.argv[2]).read_text(encoding="utf-8")
    ok = verify(response, root)
    print("PASS" if ok else "FAIL")
    sys.exit(0 if ok else 1)

왜 "키워드가 포함되면 통과"가 아니라 "정확히 한 줄, 정확한 위치"여야 하는가. 처음엔 느슨하게 만들고 싶었다 — 응답 어딘가에 그 값이 등장하기만 하면 통과시키는 식으로. 그런데 그렇게 짜면 세 가지가 동시에 무너진다.

첫째, nonce 값 자체를 브리프에 넣으면 proof 파일을 열지 않아도 답할 수 있다. 브리프에는 경로와 응답 형식만 넣고 실제 값은 넣지 않는다. 줄 전체를 비교하는 것만으로 유출된 값의 출처를 구분할 수는 없다.

둘째, 부분 일치로는 서로 다른 값을 구별하지 못한다. 값이 길어지거나 응답이 장황해지면 부분 문자열 일치에 걸릴 자리만 늘어난다. 정확히 어느 값과 일치했는지, 몇 번 일치했는지를 셀 수 없으면 "읽었다"는 판정이 흐려진다.

셋째, 정해진 위치를 요구하면 응답 형식에서 스냅샷을 염두에 두고 작성됐다는 신호까지 함께 검증하게 된다. "아무 데나 있으면 됨"이 아니라 "이 응답은 이 스냅샷을 향해 쓰였다"는 것을 형식으로 강제하는 것이다. 실전 리뷰 프롬프트에서는 응답 형식을 헤더 순서와 필수 문구 위치까지 고정해두는 편이 안전하다 — 위치가 자유로울수록 나중에 끼워 맞출 여지가 늘어난다.

그런데 nonce는 스냅샷을 읽었다는 증거일 뿐이다

nonce를 넣고 나서 한동안은 이걸로 됐다고 생각했다. 그런데 이 값은 딱 하나만 증명했다 — 응답이 해당 nonce 값을 알고 있다는 것. 값이 유출되지 않았다는 전제에서 proof 파일 접근의 정황 증거가 되지만, 다른 소스 파일을 읽고 이해했다는 증거는 아니다. 리뷰어는 여전히 진짜 코드를 보지 못했다. 스냅샷의 sources/는 브리프를 쓴 사람이 손으로 골라 담은 발췌본이다. 발췌가 잘못됐거나, 오래됐거나, 리뷰에 불리한 부분을 빼먹었다면 리뷰어는 그것도 모른 채 발췌본만 보고 통과시킨다.

리뷰어에게 실제 코드를 보여주려면 저장소를 직접 읽을 수 있는 두 번째 읽기 경로가 필요했다 — 검토 대상 브랜치를 얕게 복제한 읽기 전용 클론이다. 그런데 이 클론을 여는 순간 새 구멍이 열렸다. 읽을 수 있는 파일 시스템이 하나 더 생겼으니 nonce로 막았던 것과 같은 종류의 실수(느슨한 검사, 위치 미고정, 값의 유일성 미검증)가 더 크고 훨씬 통제하기 어려운 이 표면에서 그대로 반복될 수 있게 됐다.

읽을 권한을 준 것과 건네준 것은 다르다

클론을 만들고 워커의 샌드박스 정책에 클론 경로를 읽을 수 있는 권한을 추가했다. 권한 설정만 보면 완결된 기능처럼 보였다. 그런데 실제로 돌려보니 리뷰어 세 명 중 두 명에게는 이 기능이 몇 주 동안 완전히 헛돌았다.

알고 보니 간단한 이유였다. 클론은 호출마다 임시 디렉터리 아래 새 이름으로 만들어졌다. 그 경로에 읽기 권한은 열려 있었지만 경로가 정확히 어디인지 워커에게 알려주는 채널이 없었다. 셸이 없는 리뷰어는 그 이름을 스스로 찾아낼 수 없다 — ls도 못 치고 디렉터리 인자를 받지도 않는다. "권한이 있다"고 해서 "접근할 방법을 안다"는 뜻은 아니다. 특히 명령줄 인자 하나 받지 못하는 워커에게는 둘이 완전히 별개다.

그래서 경로를 스냅샷 루트에 파일로 적어 두는 식으로 고쳤다 — 워커가 이미 열 수 있다고 알고 있는 유일한 장소, 즉 브리프 옆이다. 그리고 검증기가 그 파일이 있는지, 안에 적힌 경로가 유효한지 확인하게 했다. 이걸 빠뜨리면 기능이 조용히 아무 일도 하지 않는다 — 에러도 안 나고 로그에 실패라고도 안 찍힌다. 그냥 리뷰어가 클론을 한 번도 열어보지 못한 채로 리뷰가 끝날 뿐이다.

이 파일은 tools/write_view_handoff.py에 둔다.

#!/usr/bin/env python3
"""읽기전용 뷰(클론)의 실제 경로를 스냅샷 루트에 적어 넘긴다."""
from __future__ import annotations

from pathlib import Path


def write_view_handoff(snapshot_root: Path, view_path: Path) -> None:
    view_path = view_path.resolve()
    if not view_path.is_dir():
        raise RuntimeError(f"뷰 경로가 존재하지 않음: {view_path}")
    (snapshot_root / "repo-view-path.txt").write_text(str(view_path) + "\n", encoding="utf-8")


def verify_view_handoff(snapshot_root: Path) -> Path:
    handoff = snapshot_root / "repo-view-path.txt"
    if not handoff.exists():
        raise RuntimeError("repo-view-path.txt 없음 — 뷰 경로를 워커에게 건네지 않았다")
    value = handoff.read_text(encoding="utf-8").strip()
    if not value or not Path(value).is_absolute():
        raise RuntimeError("뷰 경로는 비어 있지 않은 절대경로여야 한다")
    view_path = Path(value)
    if not view_path.is_dir():
        raise RuntimeError(f"기록된 뷰 경로가 실존하지 않음: {view_path}")
    return view_path

challenge-response — 뷰 안에만 있는 줄로 묻고 답하게 한다

경로를 건네고 나니 다음 질문이 이어졌다. 경로를 받은 것과 그 안의 내용을 읽은 것도 별개다. nonce가 proof 값의 보유를 확인했듯, 이번엔 "뷰를 실제로 읽었는가"를 증명할 장치가 필요했다. 방식은 비슷하다 — 뷰 안에만 존재하는 사실을 골라 질문하고 정확히 그 답을 요구한다. 다만 이번엔 "정답을 어떻게 고를 것인가"부터가 훨씬 어려운 문제였다. 순서대로 네 번 뚫렸다.

(a) 파일 안에서만 유일한 줄로는 부족하다. 처음엔 "이 줄이 이 파일 안에서 딱 한 번만 나오는가"만 확인하고 후보로 삼았다. 그런데 같은 줄이 뷰의 다른 파일에도 그대로 있으면 질문받은 파일을 열어보지 않고 다른 파일만 봤어도 답할 수 있다. 그래서 유일성은 뷰 전체를 기준으로 다시 계산해야 했다 — 파일 하나 안에서만 따진 유일성이 아니라 워커가 접근할 수 있는 모든 파일을 통틀어 따진 유일성.

(b) 부분 문자열 비교는 한 줄이 다른 줄에 포함될 때 무너진다. 정답 판정을 "이 텍스트를 포함하는가"로 짜면 한 후보 줄이 다른 후보 줄의 일부로 들어갈 때 답 하나로 질문 두 개가 동시에 맞아버린다. 서로 다른 두 가지를 확인하려던 것이 같은 내용을 중복해서 센 꼴이 된다. 그래서 비교는 반드시 줄 전체의 정확한 일치여야 한다 — 포함이 아니라 동일.

(c) 질문 자체가 답을 노출하는 경우가 있다. 문서 안에 "질문 형식을 설명하는 줄"이 들어 있을 수 있다 — 예컨대 이 챌린지가 렌더링하는 질문 문구와 똑같은 패턴의 문장이 뷰의 어느 문서에 실려 있는 경우다. 이런 줄을 후보로 뽑으면 질문을 쓰는 순간 질문 문장이 이미 답을 담게 된다. 그래서 후보를 확정하기 전에 질문 문장을 먼저 렌더링해보고 질문과 후보 줄이 서로 포함 관계라면 후보에서 제외해야 했다.

(d) 3문 3정답은 성실한 리뷰어를 거부했다. 처음엔 세 문제를 내고 셋 다 맞아야 통과로 잡았다. 그런데 실제로 뷰를 꼼꼼히 읽은 리뷰어가 번호 매겨진 목록에서 줄 하나를 잘못 짚어 셋 중 하나를 틀렸다는 이유로 통째로 거부당했다. 정직하게 일한 결과가 통제 장치 때문에 버려진 것이다. 기준을 3문 2정답으로 낮췄다 — 실수 한 번은 허용하되 절반 이상 틀리면 여전히 거부한다. 정직한 작업을 거부하는 통제는 결국 꺼진다. 게이트가 너무 엄격해서 성실한 결과까지 잡아내면 사람들은 게이트를 신뢰하는 대신 우회하거나 꺼버린다. 그렇다고 느슨하게 만들라는 말은 아니다. 얼마나 엄격하게 할지 정할 때 실제로 잡아야 할 것(조작)과 감내해야 할 것(실수)을 구별하지 못하면 그 통제는 오래 못 간다.

이 파일은 tools/challenge_response.py에 둔다.

#!/usr/bin/env python3
"""읽기전용 뷰를 실제로 읽었는지 묻고 답하게 하는 challenge-response 검사기."""
from __future__ import annotations

import random
import re
from pathlib import Path

MIN_LINE_LENGTH = 20
QUESTION_COUNT = 3
PASS_THRESHOLD = 2  # 3문 중 2정답 — 3정답을 요구했다가 정직한 리뷰어를 거부한 적이 있다

QUESTION_LINE_RE = re.compile(r"^(?P<idx>\d+)\. QUOTE_LINE (?P<path>.+):(?P<lineno>\d+)$")


def _iter_view_lines(view_root: Path):
    for path in sorted(view_root.rglob("*")):
        if path.is_symlink() or not path.is_file() or not path.resolve().is_relative_to(view_root.resolve()):
            continue
        rel = path.relative_to(view_root)
        try:
            text = path.read_text(encoding="utf-8", errors="strict")
        except (UnicodeDecodeError, OSError):
            continue
        for lineno, line in enumerate(text.splitlines(), start=1):
            stripped = line.strip()
            if len(stripped) >= MIN_LINE_LENGTH:
                yield rel, lineno, stripped


def _build_exclusion_corpus(*handed_dirs: Path) -> set[str]:
    """워커가 이미 받은 모든 텍스트(brief + sources) — 정답 후보에서 제외한다."""
    corpus: set[str] = set()
    for handed in handed_dirs:
        if not handed.exists():
            continue
        for path in handed.rglob("*"):
            if path.is_file():
                try:
                    text = path.read_text(encoding="utf-8", errors="strict")
                except (UnicodeDecodeError, OSError):
                    continue
                corpus.update(ln.strip() for ln in text.splitlines() if ln.strip())
    return corpus


def _render_question(rel_path: Path, lineno: int) -> str:
    return f"QUOTE_LINE {rel_path}:{lineno}"


def select_challenge(
    view_root: Path, handed_dirs: list[Path], count: int = QUESTION_COUNT, seed: int | None = None
) -> list[tuple[Path, int, str]]:
    """뷰에서만 나오고, 뷰 전체에서 유일하고, 질문 자체가 답을 드러내지 않는 줄을 count개 고른다."""
    if type(count) is not int or count < 1:
        raise ValueError("count는 양의 정수여야 한다")
    by_text: dict[str, list[tuple[Path, int]]] = {}
    for rel, lineno, text in _iter_view_lines(view_root):
        by_text.setdefault(text, []).append((rel, lineno))

    exclusion = _build_exclusion_corpus(*handed_dirs)

    candidates: list[tuple[Path, int, str]] = []
    for text, locations in by_text.items():
        if len(locations) != 1:
            continue  # 파일 안에서만 유일한 게 아니라, 뷰 전체에서 유일해야 한다
        if any(text in line for line in exclusion):
            continue  # 워커가 이미 받은 내용에도 있으면 정답이 아니다
        rel, lineno = locations[0]
        question = _render_question(rel, lineno)
        if question in text or text in question:
            continue  # 질문 문장이 후보 줄 안에 이미 있으면 자기지시적이라 버린다
        candidates.append((rel, lineno, text))

    rng = random.Random(seed)
    rng.shuffle(candidates)
    if len(candidates) < count:
        raise RuntimeError(f"뷰에서 유일하고 안전한 줄을 {count}개 찾지 못함 (가용 {len(candidates)}개)")
    return candidates[:count]


def write_challenge(
    view_root: Path, handed_dirs: list[Path], out_path: Path, seed: int | None = None
) -> None:
    picked = select_challenge(view_root, handed_dirs, seed=seed)
    lines = [
        "다음 각 질문에, 지정된 파일의 지정된 줄 내용을 정확히 그대로 답하라.",
        "형식: ANSWER_<번호>: <줄 내용 그대로>",
        "",
    ]
    for i, (rel, lineno, _text) in enumerate(picked, start=1):
        lines.append(f"{i}. {_render_question(rel, lineno)}")
    out_path.write_text("\n".join(lines) + "\n", encoding="utf-8")


def verify_challenge(
    view_root: Path, out_path: Path, response_text: str, pass_threshold: int = PASS_THRESHOLD
) -> bool:
    """답은 저장된 값과 비교하지 않는다 — 매번 고정된 읽기 전용 뷰에서 다시 계산한다."""
    if type(pass_threshold) is not int or not 1 <= pass_threshold <= QUESTION_COUNT:
        return False
    try:
        questions = []
        for line in out_path.read_text(encoding="utf-8").splitlines():
            match = QUESTION_LINE_RE.fullmatch(line.strip())
            if match:
                questions.append(match)
        if len(questions) != QUESTION_COUNT or {m["idx"] for m in questions} != {"1", "2", "3"}:
            return False
        locations = set()
        expected_values = set()
        correct = 0
        root = view_root.resolve()
        for m in questions:
            rel = Path(m["path"])
            lineno = int(m["lineno"])
            path = (root / rel).resolve()
            if rel.is_absolute() or ".." in rel.parts or not path.is_relative_to(root) or lineno < 1:
                return False
            location = (path, lineno)
            if location in locations:
                return False
            locations.add(location)
            expected = path.read_text(encoding="utf-8").splitlines()[lineno - 1].strip()
            if len(expected) < MIN_LINE_LENGTH or expected in expected_values:
                return False
            expected_values.add(expected)
            answers = [ln.strip() for ln in response_text.splitlines() if ln.strip().startswith(f"ANSWER_{m['idx']}:")]
            if len(answers) > 1:
                return False
            if answers and answers[0].split(":", 1)[1].strip() == expected:
                correct += 1
        return correct >= pass_threshold
    except (OSError, ValueError, IndexError):
        return False

질문 파일과 뷰는 신뢰된 조정자가 만들고 워커는 수정할 수 없어야 한다. 뷰는 검토할 커밋·파일 해시로 고정하고 생성부터 검증까지 바뀌지 않게 유지한다. 아래 코드는 그 OS 격리나 커밋 고정을 구현하지 않는다. 고정되지 않은 뷰를 다시 읽는 것만으로 최초 질문의 입력과 같다고 증명할 수 없다.

답을 검증할 때 저장해둔 정답과 비교하지 않고 매번 view_root에서 다시 읽어 계산한다는 점을 눈여겨봐야 한다. 정답을 질문과 함께 봉투에 담아 보내면 그 봉투가 위조·재사용될 수 있는 새로운 표면이 된다. 질문과 답을 같은 곳에 나란히 두기보다 질문은 저장하되 답은 고정된 뷰에서 다시 계산한다. 그 사이 뷰가 달라졌으면 해당 검증은 무효다.

이 방식이 증명하지 못하는 것

이 장치의 경계는 정직하게 밝혀 둬야 한다. 이 challenge-response는 "이 격리 조건 아래서 그 줄들이 산출됐다"는 것을 증명할 뿐 "바로 이 사본을 열어서 그 줄을 봤다"는 것까지 증명하지는 않는다. 미묘하지만 가볍게 넘길 차이가 아니다.

이 장치는 한 가지를 전제로 한다. 리뷰어에게 셸도, 저장소를 조작할 도구도 없다면 질문의 정답을 스스로 계산해낼 방법은 뷰를 여는 것 말고는 없다. 그런데 리뷰어가 같은 코드의 다른 공개된 사본을 이미 어떤 경로로든 알고 있었다면 — 예컨대 저장소가 공개돼 있어서 사전 지식으로 갖고 있었거나 전혀 다른 경로로 같은 내용을 이미 본 적이 있었다면 — 이 검사는 그 사전 지식과 "지금 이 뷰를 열어서 읽었다"를 구분하지 못한다. 이 장치는 격리된 조건에서 나온 산출까지만 검증한다. 인식론적으로 완전한 출처 증명에는 미치지 못한다.

이 책의 신뢰도는 과대주장하지 않는 데 달려 있다. 이 검사를 넣고 여러 라운드를 돌리면서 문서에는 "증명됐다"고 적혀 있었지만 실제로는 아무도 확인하지 않은 채 방치된 주장이 여러 번 나왔다 — 코드는 존재하는데 호출자가 없거나, 검사 로직은 있는데 재도출이 아니라 저장된 값과 자기 자신을 비교하고 있거나. 그때마다 같은 방법으로 고쳤다. 그 장치가 무엇을 보장하고 무엇을 보장하지 않는지를 문서에 다시 정확히 적었다.

직접 확인하는 법

위 코드 네 벌을 지정된 파일에 저장하고 다음 여섯 가지를 일부러 깨뜨려서 빨간불이 켜지는지 확인하라. 통과만 확인하고 끝내면 검증한 게 아니다.

  1. nonce 없는 응답을 넣어본다. verify_source_access.py에 첫 줄이 SOURCE_ACCESS_PROOF:...가 아닌, 그럴듯하지만 무관한 리뷰 텍스트를 넣어라. FAIL이 나와야 정상이다.
  2. 검사를 일부러 느슨하게 바꿔본다. nonce 값을 리뷰 문단 중간에 파묻은 응답 — 예컨대 코드 세 곳을 확인했고 문제없음. 참고로 SOURCE_ACCESS_PROOF:<값>도 확인함. — 을 만들어라. 원래의 verify()(전체 줄 일치)는 이걸 거부해야 정상이다. 이제 검사를 nonce in response_text로 느슨하게 바꿔서 같은 응답을 다시 넣어보라 — 통과해버릴 것이다. 형식을 지키지 않은 응답, 즉 그 자리에서 진지하게 다시 옮겨 적지 않고 어딘가에 끼워 넣기만 한 응답도 통과한다. 그래서 "포함이면 통과"는 위험하다. 원래대로 되돌려라.
  3. repo-view-path.txt를 지워본다. 클론은 만들어져 있고 권한도 열려 있는데 이 파일만 없는 상태를 만들어라. verify_view_handoff()가 RuntimeError를 던지는지 확인한다 — 던지지 않는다면 권한과 전달을 혼동하고 있는 것이다.
  4. 후보 줄을 뷰의 두 파일에 똑같이 복제해본다. select_challenge()를 다시 실행해 그 줄이 후보 목록에서 빠지는지 확인한다 — len(locations) != 1 체크가 살아있다면 빠져야 한다.
  5. 정답의 일부만 잘라서 답해본다. verify_challenge()에 기대값의 앞부분만 담은 답을 넣어라. 부분 일치가 아니라 전체 일치를 요구하므로 오답 처리돼야 한다.
  6. 3문 중 2문만 정확히 답하고 하나는 살짝 틀리게 넣어본다. 통과해야 정상이다(임계값 2). 이어서 1문만 맞혀본다 — 이번엔 거부돼야 정상이다. 둘 다 확인해야 임계값이 양쪽 방향으로 제대로 작동하는지 안다.

여섯 개 중 하나라도 기대와 다르게 나오면 이 장에서 설명한 사고 중 하나가 그 형태로 재발한 것이다.
