AI가 일했다는 증거

Claude Code 멀티에이전트 실전 운영

Claude Code에 일을 시키고 "다 됐다"는 말을 어떻게 확인하는지 다룬 책이다. 원래 팔던 책인데 전부 무료로 풀었다. 아래에서 장마다 전문을 읽을 수 있다.

장

  1. 0장 — 왜 "exit 0"은 증거가 아닌가

    워커가 "완료"라고 답했고 종료코드도 0인데, 그 작업이 실제로 일어났는지 확인할 방법이 없다

  2. 1장 — 지시가 몇 턴 만에 흐려지는 문제

    CLAUDE.md 에 규칙을 써 두어도 몇 턴 지나면 지켜지지 않는다

  3. 2장 — CLAUDE.md를 오래 고쳐 쓸 수 있게 짜기

    사고가 날 때마다 규칙을 덧붙이다 보니 CLAUDE.md 가 감당 못 할 크기가 됐다

  4. 3장 — 세션이 끊겨도 이어지게

    세션이 끊기면 다음 세션이 이미 기각한 설계안을 다시 제안한다

  5. 4장 — 직접 할까 위임할까

    직접 5분이면 될 일을 위임했다가 15분짜리 왕복이 됐다

  6. 5장 — 실패했을 때 무엇을 올릴 것인가

    실패하면 반사적으로 effort 를 올린다. 또 실패한다. 원인은 딴 데 있었다

  7. 6장 — 위험한 명령을 안전하게 위임하기

    승인 버튼을 하루에 수백 번 누르다 보면 내용을 안 읽고 누르게 된다

  8. 7장 — 위임 증거 만들기

    40KB 짜리 파일 셋을 5초 만에 리뷰했다고 답이 왔다. 파일을 연 적이 없었다

  9. 8장 — 가드가 진짜 작동하는지 증명하기

    몇 주째 초록불이던 검사가, 사고가 난 뒤 보니 한 번도 빨간불이 된 적이 없었다

머리말 — 초록불이 거짓말을 하기 시작할 때

처음 서브에이전트에 코드 리뷰를 맡겼을 때가 기억난다. 브리프를 정성껏 쓰고, 파일 경로를 정확히 적어주고, 돌렸다. 3분 뒤에 잘 정리된 리뷰가 돌아왔다. 지적 사항이 네 개 있었고 전부 그럴듯했다. 종료코드는 0이었다.

그중 두 개가 지적한 코드는 그 파일에 존재하지 않았다.

그때 알았다. 나는 그 에이전트가 파일을 읽었는지 한 번도 확인한 적이 없었다. 브리프에 경로를 적어줬을 뿐이다. 그리고 언어모델은 경로 이름과 프로젝트 맥락만으로도 대단히 그럴듯한 리뷰를 쓸 수 있다. 종료코드 0은 그 프로그램이 성공으로 처리하고 끝났다는 신호였다. 일이 제대로 됐는지는 따로 확인해야 했다.

이 책은 그 지점에서 시작한다.

시중에는 Claude Code 자료가 많다. 대부분 "CLAUDE.md에 이렇게 쓰세요", "이런 커맨드가 있습니다"에서 멈춘다. 그건 출발선이다. 실제로 며칠만 굴려보면 이런 질문에 부딪힌다.

  • 규칙을 써놨는데 왜 몇 턴 지나면 무시되는가
  • 서브에이전트가 진짜로 그 파일을 읽었는지 어떻게 아는가
  • "다 됐습니다"를 어떻게 믿는가
  • 세션이 끊기면 왜 다음 세션은 처음부터 헤매는가
  • 이 작업을 직접 할지 위임할지, 매번 감으로 정하는 게 맞는가
  • 실패했을 때 무엇을 올려야 하는가 — 모델인가, effort인가, 아니면 내 명세인가
  • 안전장치를 만들어뒀는데 그게 실제로 작동하는지는 어떻게 아는가

이 책에서는 그 질문들에 답한다. 답의 대부분은 프롬프트를 더 잘 쓰는 것이 아니라 구조를 만드는 것이다. 규칙의 길이·충돌·불러오는 경로를 확인하고, 반드시 지켜야 하는 조건은 실행 단계에서 검사해야 한다.

이 책이 쓰인 방식

여기 실린 장치들은 설계실에서 나오지 않았다. 전부 사고가 나서 생겼다.

한 검증 과제를 열 라운드 넘게 돌리면서 매 라운드 독립 리뷰어에게 판정을 받았다. 거의 매번 거부당했다. 더 뼈아프게도 지적의 상당수는 직전 라운드에 구멍을 막으려고 내가 새로 넣은 코드를 겨냥했다. fail-open을 닫으려고 넣은 장치가 새로운 fail-open을 만들었다. 검사를 등록한 뒤 그 대상 스크립트를 고치고 게이트를 다시 안 돌린 채 커밋하는 바람에 커밋 메시지의 수치가 그 트리와 어긋난 적도 있다.

그래서 각 장을 "이렇게 하면 됩니다"로 끝내지 않는다. 반드시 "그런데 그걸로도 부족했던 지점" 절을 둔다. 이 책의 값어치는 그 절에 있다. 해법만 실린 책을 따라간 독자는 내가 이미 빠졌던 함정에 그대로 빠진다.

같은 이유로, 각 장에서는 그 장치가 증명하지 못하는 것도 밝힌다. 과대주장은 나중에 더 큰 대가로 돌아온다.

읽는 법

1~3장은 순서대로 읽고 작은 프로젝트에 적용해 보라. 지시가 흐려지는 문제(1장), CLAUDE.md 설계(2장), 세션 인계(3장)를 다룬다. 적용 시간과 효과는 환경마다 다르다. 뒤의 장으로 넘어가기 전에 각 장의 확인 절차부터 돌려보면 좋다.

4~5장은 판단의 장이다. 직접 할지 위임할지, 실패했을 때 무엇을 올릴지. 코드보다 표가 많다. 인쇄해서 옆에 붙여두는 용도로 썼다.

0장, 6~8장이 이 책의 본론이다. 증거의 등급(0장), 위험 명령의 보조 차단(6장), 위임 증거 만들기(7장), 그리고 가드 자체를 증명하기(8장). 7장과 8장은 어렵다. 대신 다른 데 없다.

각 장 끝에는 "직접 확인하는 법"이 있다. 반드시 하라. 특히 안전장치를 다루는 장에서는 일부러 깨뜨려서 빨간불이 되는지 확인해 본다. 한 번도 빨간불이 된 적 없는 검사는 "통과"가 아니라 "실행된 적 없음"일 수도 있다.

전제 지식

독자는 Claude Code를 설치했고, CLAUDE.md를 써봤고, 서브에이전트를 한 번이라도 굴려본 사람으로 잡았다. 설치법과 기본 사용법은 다루지 않는다.

코드는 Python 3.10 이상과 셸을 기준으로 썼다. 파일 전문과 앞서 정의한 함수를 불러 쓰는 실습 조각을 구분해서 읽어야 한다. macOS·Linux용 파일 권한 예제는 Windows에 그대로 적용되지 않는다. 설치 예제의 경로·해시·조각 파일은 자기 환경에 맞게 채운다. 위험 명령은 실제로 실행하지 말고 임시 디렉터리에서 훅에 JSON 문자열로만 넣어 시험한다.

2026-09-28 기술 검증판에서는 원고의 코드 블록을 추출해 정상 입력과 반례를 실행했다. Claude Code 동작 설명은 확인일의 공식 문서와 대조했다. 과거 사고담의 시간·횟수는 저자의 경험 서술이며 이번 검증에서 재현한 측정값은 아니다. 실제 서비스 연결, 모델의 규칙 준수율, 운영 환경의 보안 격리까지 검증한 것은 아니다.

이 책에 실리지 않은 것

정직하게 밝혀둔다.

  • 벤치마크와 비용 실측표. 모델 가격과 성능은 이 책이 인쇄되는 순간부터 낡는다. 대신 "어떻게 측정할 것인가"를 실었다.
  • 특정 모델에 대한 추천. 4~5장은 모델명 대신 "상위 티어 / 중간 티어 / 경량 티어"로 쓴다. 이름은 바뀌고 구조는 남는다.
  • 완결된 프레임워크. 이 책은 라이브러리를 팔지 않는다. 여러분이 자기 환경에 맞게 만들 수 있도록 메커니즘과 그 실패 양상을 설명한다.
