## 직접/위임 판정과 실패 진단

- 워커의 모델·effort가 배차 설정에 고정된 구성에서는 위임할 때 고르는
  것이 "어느 워커냐" 하나뿐이다. 이건 그런 운영 구성의 이야기이고 Claude
  Code 전체의 제약이 아니다 — 쓰는 런타임에서 서브에이전트의 모델·effort를
  바꿀 수 있는지부터 확인한다.
- 직접 실행을 고를 때 조작 가능한 축은 모델과 effort 두 개뿐이다. 판정을
  시작하기 전에 "지금 내가 조작할 수 있는 축이 무엇인가"부터 확인한다.
- 명세(범위·완료조건·검증 방법)가 실행 가능한 상태가 아니면 위임이든
  직접이든 먼저 멈추고 명세부터 정한다. 불분명한 목표로 비싼 실행을
  낭비하는 것이 가장 비싼 실수다.
- 물량이 적고 인계비용·컨텍스트의존도가 크면 직접 실행한다. 위임의 고정비
  (새 컨텍스트 구축 + 명세 작성)가 산출물보다 클 때는 위임이 진다.
- "위임하면 무조건 싸다"고 가정하지 않는다. 위임 워커 풀에 경제형이 없어도
  위임으로 병렬성과 메인 컨텍스트 보존은 얻을 수 있다. 비용이 줄었는지는
  워커 가격뿐 아니라 캐시·토큰·검수 시간까지 실제로 재야 안다. 직접-위임
  실측 비교가 없으면 비용 차이는 "측정되지 않음"이라고 말한다.
- 서브에이전트가 실패하면 반사적으로 effort나 모델 티어부터 올리지 않는다.
  먼저 원인을 진단한다 — 추론깊이 부족 / 모델 역량 부족 후보 / 명세 부실 /
  구현 버그 / 도구·인프라 문제 / 과잉 투입 / 역할·벤더 불일치. 먼저 시험할
  대응은 분류마다 다르다. 최고 effort에서 실패했다는 사실만으로 모델 역량
  부족이라고 확정하지 않는다.
- 가장 흔한 오진은 명세 부실을 모델 역량 부족으로 착각하는 것이다. 통과
  기준을 소리 내어 다시 읽어 애매한 구석이 있다면 명세부터 고친다.
- 재시도할 때는 축을 딱 하나만 바꾼다. 모델과 effort를 동시에 바꾸면
  다음번에 무엇이 원인이었는지 알 수 없다.
- 인증 만료·네트워크 오류 같은 도구·인프라 문제를 모델 품질 실패로 기록
  하지 않는다. 그 기록이 나중에 잘못된 판단 근거가 된다.
